# Tiny Adventurers — Technical Documentation

Audience: developers and coding agents working on the code. For gameplay see [PLAYER_GUIDE.md](PLAYER_GUIDE.md); for open work see the [GitHub issues](https://github.com/migosoft/TinyAdventurers/issues) ([CLAUDE.md](../CLAUDE.md) "Work tracking").

## 1. Overview

A browser multiplayer dungeon crawler.

- **Server:** Rust. It is authoritative: it owns the lobby, dungeon generation, the simulation (movement, combat, AI, bosses) and what every player is allowed to see.
- **Client:** TypeScript + Phaser 3. It renders and sends inputs.
- **Responsiveness:** the client predicts its own movement and attacks so input never waits for the network.

```
Browser (Phaser client)  ──WebSocket /ws, MessagePack──►  Rust server (axum + tokio)  ──sqlx──►  PostgreSQL 17
  ▲  prediction, interpolation, rendering                    lobby (Mutex) + one tokio task per run   accounts, sessions,
  │                       ──HTTP JSON /api/* (login)──►      account + character API                  characters (+ JSONB progress)
  └──────────────── per-player snapshots (30 Hz) ◄──────────  60 Hz simulation, FOV-filtered
```

Two Docker containers:
- `game` serves the static client, the JSON API and the WebSocket on port 8080.
- `db` is PostgreSQL 17. It holds accounts and characters and is not published to the host.

| Client production build | `cd client && npm run build` (runs the atlas build, tsc, vite) |

Server tests in Docker (Git Bash on Windows). `docker-compose.test.yml` starts a throwaway PostgreSQL (in RAM) next to `rust:1-slim-bookworm`. The external volumes `ta-cargo` and `ta-target` cache crates and builds; create them once with `docker volume create`.

```sh
MSYS_NO_PATHCONV=1 docker compose -f docker-compose.test.yml run --rm test
docker compose -f docker-compose.test.yml down
```

**Database tests:**
- The database tests (`db::tests`, `stats::tests`, and `lobby::tests::a_finished_run_banks_…`) run only when `DATABASE_URL` is set. Without it they pass without checking anything.
- Each test creates its own database `ta_test_<random>` on that server, so they run in parallel.

**Generated files.** `cargo test` (re)writes the following, which must be committed:
- `client/src/generated/*.ts`: the protocol types, from `#[derive(TS)] #[ts(export)]`
- `client/src/generated/defs.ts`: kinds, anim ids, flags, tile ids, constants, class and ability numbers
- `client/src/generated/fixtures.json`: collision/FOV test vectors

**After changing `protocol.rs` or anything in `defs/`, run `cargo test`.** Then rebuild the client.

## 4. Protocol

**Accounts API (`/api`, JSON, `api.rs`).** The request and response types are ts-rs exported (`Credentials`, `PasswordConfirm`, `NewCharacter`, `Me`, `ApiError`).

| Request | Effect |
|---|---|
| `POST /api/register {name, password}` | Creates the account and logs in (sets the cookie). Answers `Me`. |
| `POST /api/login {name, password}` | Sets the cookie. Answers `Me`. A wrong name and a wrong password get the same 401. |
| `POST /api/logout {}` | Deletes the session, clears the cookie and closes the account's WebSocket. |
| `DELETE /api/account {password}` | Needs the password again. Deletes the account with its sessions and characters (cascade) and closes its WebSocket. |
| `GET /api/me` | `Me{name, characters: CharacterInfo[], max_characters}`, or 401. |
| `POST /api/characters {name, class}` | 201 with `CharacterInfo`. 409 if the name is taken or the account already has 8 characters. |
| `DELETE /api/characters/{id}` | 204. 409 while that character is in a room or run, 404 if it is not the account's. |

- Errors are `{error: "text for the player"}`.
- Non-GET requests must send `Content-Type: application/json` (415 otherwise).
- The responses carry `Cache-Control: no-store`.

**WebSocket.**
- `/ws` uses binary frames and MessagePack.
- The upgrade needs a valid session cookie (401 otherwise).
- When the browser sends an `Origin` header, it must match `Host` (403 otherwise).
- Server → client: `rmp_serde::to_vec_named` (structs as maps). Client → server: `@msgpack/msgpack` objects.
- Enums use an internal tag `t`, e.g. `{ t: "Input", seq, mx, ... }`. Variant fields must not be named `t`.

**Client → server (`ClientMsg`)**
- `SelectCharacter{id}`: play as one of the account's characters. The server loads it (ownership checked) and answers with `Character`. It is refused while in a room. The client sends it when a roster card is clicked, after connecting.
- `CreateRun{name}`, `JoinRun{run_id}`: need a selected character ("Choose a character first"). A room's kind (debug or normal) is fixed by its creator's account flag; `JoinRun` refuses the other kind, and a character of the other kind than the connection is refused (kick) too.
- `LeaveRun`, `SetReady{ready}`
- `SelectBoss{boss}`: host only, before the start. `null` = random.
- `StartRun`: host only. Turns the room's level and boss choice into a `LevelChoice` (`{level: "Dungeon", boss}`, tag `level`). There is no level picker yet: every room plays `LevelId::Dungeon`.
- `BuyAttribute{attr}`, `BuyNode{node}`, `Respec`, `Equip{slot, item: Option}`, `SetLoadout{primary, secondary}`: change the selected character's build (§11a "Attribute shop, skill trees and keystones"). Refused with "Not during a run." in a running run and "Not while ready." while Ready; allowed in the lobby and a waiting room otherwise.
- `DebugGrantItem{item}`: debug accounts only; puts a copy of a hero item into the inventory (saved). Also refused during a run and while Ready.
- `DebugBuyAttribute{attr}`, `DebugBuyNode{node}`, `DebugRespec`: debug accounts only (else "Debug is off."); `BuyAttribute`, `BuyNode` and `Respec` without the XP or coin cost (`progress::Change::FreeAttr/FreeNode/FreeRespec`). The tree's neighbour and Attribute checks stay. Free buys do not count in `xp_spent`, so a later respec refunds only XP that was paid. Saved on the character, and only if the account is a debug account at save time (see "Debug accounts" in §11a). The hub sends them instead of the normal buys when `Welcome.debug` is set.
- `Input(InputMsg)`: one per 1/60 s step: `seq, mx, my, aim, aim_dist, primary/secondary: Option<shot_id>, view_lag, rtt, act`. `act` is true for the one input after an E press: the hero uses the nearest object in reach (see "World objects" in §5). On the wire it is a bare array `InputW` in that field order (`wire.ts` `packInput`, aim as f32); the server recognizes the MessagePack array marker in the first byte. A `t`-tagged `Input` map is still accepted.
- `Ping{time}`, `Spectate{dir}`, `DebugDarkvision{ratio}`: sets the sender's own hero darkvision (a share of its vision, 0 to 1). The server honours it only in a debug run. The client sends it from F4 (§10). There is no `Debug{on}` message: every hero of a debug run starts in debug mode.
- `DebugEffect{kind}`: puts the `EffectKind` with that id on the sender's own hero for its default duration (honoured only in a debug run). The client sends it from F8 (§10).
- `DebugImmortal{on}`: in a debug run (else ignored): `on: false` sets `Player.mortal`, so hits and terrain hurt as in a normal run (`Player::immortal()` = `debug && !mortal`); `on: true` undoes it. Debug stays on (paths, F4, F8). The client sends it from F9 (§10).

**Server → client (`ServerMsg`)**
- `Welcome{id, debug}` (`debug` is the account's flag, read from `accounts.debug` when the WebSocket connects; a database error refuses the connection), `Lobby{runs}` (only the rooms of the connection's own kind), `Room{run_id, name, host, players, level, boss}`
- `Character(CharacterInfo)`: the selected character, sent after `SelectCharacter`, a purchase and banking. Fields: `id, name, class`, unspent `xp`, `total_xp`, `coins`, `bought` (Attribute points), `nodes`, `equipment`, `inventory`, `loadout`, `xp_spent`, `respec_price`, `prices` (the XP price of the next point of each Attribute, in `Attr` order) and `sheet` (a `SheetSummary`: per-Attribute lines with their sources, HP, speed, weight, push, the CON and WIL saves, resistances, effect resistances, proficiencies and `loadout_error`). The same type is used in `Me`. `Room.players` carry each member's `loadout` and the `weapons` that will play.
- `Room.players` take name and class from each member's character.
- `Error{msg}` right before the server closes a socket explains why (logged in from another window, logged out, account deleted).
- `RunStarted(RunStartInfo)`: `debug` (a debug run: every hero is in debug mode), the `level` (`LevelId`), full tile grid as bytes, player list, own entity id, spawn, the hero's resolved `speed`, `abilities` and `fallback` (§11a), and `lights: Vec<LightInfo>`: every static light at the start (torches and lava) as `LightInfo(id, kind, colour, x, y, on)` (tile coordinates, colour 0xRRGGBB, `kind` a `LightKind` id)
- `Snap(Snapshot)`: 30 Hz. Contains `tick`, `ack`, entities, `me` (`SelfState`: authoritative position/dash/cooldowns), optional boss bar, events, `srv_ms`, and `lights: Vec<MovingLight>`, the lit moving lights near the viewer (see §7). See "Compact snapshots" below for the wire form.
- `RunEnded{victory, level, boss, time, stats}`: `boss` is the level's end boss, `null` for a level without one (the end screen then shows `LEVEL_TEXT[level]`, `ui/endText.ts`). Debug runs bank like normal ones. `stats` include each player's `xp` and `coins`.
- `Pong{time}`, `Error{msg}`, `DebugPath{on, immortal, points, ogre}` (`immortal` drives the badge's immortal/MORTAL text)

**Compact snapshots** (`wire.rs`, `wire.ts`, spec in [compact-snapshots.md](compact-snapshots.md)):
- A snapshot is sent as a bare array `SnapW = [tick, ack, ents, me, boss, ev, srv_ms, drain, lights]` (`lights`, field 9, is a list of `LightW = [x, y, kind, colour?]`: positions scaled like entity positions, the colour left out when it is the kind's default), not as a `t`-tagged map. The client sees an array, unpacks it with `unpackSnap` into the readable `Snapshot` and dispatches it as `{t: 'Snap', ...}`, so the game code only knows `Snapshot`.
- Entity and event positions are whole numbers in 1/16 px (`CONST.POS_SCALE`). MessagePack stores them in 3 bytes up to 4096 px and in 5 bytes beyond, so bigger maps need no change.
- Entity `aim` is one byte, 1/256 of a full turn; the client turns 129–255 back into negative angles and 128 into +π, so it gets (−π, π] like `atan2` on the server (the staff swing in `EntityView` uses the raw angle).
- Events are arrays starting with a number code (`EV` in `defs.ts`, order of the `Ev` variants). `Tile` keeps tile coordinates.
- `me` (position, dash, cooldowns) and all hp/damage numbers keep their exact values; prediction needs them.
- `SelfW` (`me`) element 13 is the viewed hero's darkvision as a percentage in a u8 (`SelfState.darkvision`; a spectator gets the teammate's). The client uses it for the greyscale mask and the F3 line.
- `SelfW` elements 14 to 17 are the effect fields: `vision` (the viewed hero's vision in tiles through its effects, used by `LightView` instead of a constant), `effects` (the own hero's `[EffectKind id, seconds left]` pairs, for the HUD icons), `speed_mul` and `no_act` (prediction). `EntSnap` gets a trailing element `effects`, a `u16` bitmask of `EffectKind` ids for creatures (`[..., flags, extra, effects]`; the client reads it with `has(bits, EFFECT.x)`).
- Adding a field to `Snapshot`, `SelfState`, `EntSnap`, `BossBar`, `Ev` or `InputMsg` means adding it to the wire type, `encode_snap`/`ev_w`, `unpackSnap`/`packInput` and `sample_snapshots`.

**`EntSnap`** (the readable form) is a compact array: `[id, kind, x, y, hp 0-255, anim, aim, anim_ms, flags, extra]`.
- `kind`, `anim` and `flags` come from `defs/kinds.rs`. They are exported to `defs.ts` as `KIND`, `ANIM` and `FLAG`. `FLAG.AIRBORNE` marks the flying dragon; `ANIM.TakeOff`, `Land` and `Bite` are the dragon's.
- `extra` for projectiles is `(owner_id << 16) | shot_id`, for monsters the owner id, for fire patches the remaining life in ms.
- Barrels (`KIND.Barrel` 81) send `anim` 0 at rest, 1 while the fuse burns, 2 while falling into a chasm and 3 while sinking in deep water, with `anim_ms` since it started. They are filtered by line of sight like chests.
- Torches (`KIND.Torch` 82) send `anim` 1 lit or 0 out and `extra` = the `TorchSide` (0 `Face`, 1 `West`, 2 `East`). They are sent when in the viewer's sight, lit or not (§7); their light reaches the client through the start info and the light events.
- Chests (`KIND.Chest`) send `anim` 1 once opened, with `anim_ms` since the opening. A mimic that still looks like a chest is a normal monster with the `HIDING` flag (`FLAG.HIDING` 1; `Monster.hiding`); the client draws it as a closed chest. `FLAG.DORMANT` (8, `Monster.dormant`) is the other waiting state, see "Hiding and dormant" in §5. An ally (the wolf) sends its owner's id as `extra`.

**Events (`Ev`)** are collected during the ticks between snapshots. Positional events are FOV-filtered per player (except hits and explosions by heroes, see §7):
- `Dmg{x, y, v, crit, p, ty, imm}`: `ty` is the `DamageType` with the largest share of the hit (the client picks the number's colour from it, `game/damage.ts`); `imm` is set when the resistances reduced a non-zero hit to 0 (the client shows "immune"). On the wire: `[code, x, y, v, crit, p, ty, imm]`.
- `Zap{x, y, x2, y2}` (wire code 15): one jump of Chain Spark, sent to the whole party; the client draws a jagged violet line for 0.18 s.
- `Heal{x, y, v, p}` (`p`: on a hero or an ally, like `Dmg.p`), `Growl{id}` (wire code 14: the wolf `id` growls; sent to the whole party with no position, see "Companions" in §5), `Boom{k}`: `k` 13 is Purify's white-gold ring, 12 Haste's yellow ring, 11 War Cry's red-orange ring (with a shake for the own hero), 10 Frost Nova's blue ring (the codes 10 to 13 are plan 3b's; Ground Slam lands with the dust shockwave 5), 9 is the wolf's green nature puff (summon, reappear, vanish), 8 is a chest smashed (wood splinters, `Effects.splinters`), 7 a barrel explosion (6 is the lich's nova, 5 a dust shockwave).
- `Died`, `Raise`, `Immune`
- `Effect{id, kind, on}` (wire code 13): an effect started (`on`) or ended on an entity (§5 "Status effects"). For a hero it follows the `on_hero` rule, for a monster it needs sight and light. The client ignores it (the marks are drawn from the snapshot bitmask); it is the hook for effect sounds later.
- `Light{id, on, colour}` (wire code 10), `LightAdd{id, kind, colour, x, y, on}` (11), `LightRemove{id}` (12): a static light was switched or recoloured, created or removed. Sent to everyone without a position (not filtered), so every client's light map stays in step; `Light` carries the current state. A light added while the run is built goes out in `RunStartInfo.lights` instead.
- `Tile`: boss hall entrance sealed (force field)
- `Msg`
- `Coins{x, y, v}`: coins found (chest or kill). Sent to every player, not FOV-filtered, because the whole party gets them; the client adds `v` to the HUD counter while alive.
- `Sink{id, x, y, how}`: a hero or a monster is lost to the terrain: `how` 0 falls into a chasm, 1 drowns, 2 climbs back out (debug mode). A hero's `Sink` is not FOV-filtered. The client plays the fall or drown animation and leaves no skull when the following `Died` arrives. Monsters sink the same way (`how` 0 or 1 only); a monster's `Sink` is FOV-filtered (sent with its position) and, like a hero's, is followed by `Died` when the sinking ends (`kill_monster`).

## 5. Server simulation (`run/`)

**Task model.**
- The lobby is an `Arc<Mutex<Lobby>>`.
- `Lobby::start` creates a `Run` and spawns `run_task`.
- `run_task` runs a fixed 60 Hz loop:
  1. drain `RunCmd`s (inputs, spectate, debug, leave) from the mpsc channel
  2. `step()`
  3. send debug paths every 30 ticks
  4. send snapshots every 2 ticks
  5. end on victory/defeat (after a 3 s delay) or when everyone has left, then call `lobby.run_finished`.

**Levels (`run/levels/`).** A run plays one level type. `Run { layout, level, … }`:
- `layout: Layout` (`dungeon/mod.rs`) is what every level fills: `map`, enemy `spawns`, `chests` and `player_spawns`. `Run::new(id, members, seed, LevelChoice)` calls `Level::build`, which returns the layout and the level's own state; then it places the heroes, the shared enemies (each through `Level::enemy_type`, the demon dungeon's swap) and the chests, and last calls the level's `populate`.
- `level: Level` is an enum, one variant per level type: `Dungeon(DungeonLevel)` today (plus `Test`, only in tests, with nothing but default hooks). It answers `id()` (`LevelId`), `boss()`/`boss_mut()` (its `BossEncounter`, if any) and `boss_id()`, and forwards the hooks through the `dispatch!` macro.
- **`LevelRules`** (`levels/mod.rs`) is the trait each level type implements. Its hooks are associated functions taking the whole `&mut Run` (so the level's state stays in `run.level` while they run), and each has a default body, so a level overrides only what it needs:

| Hook | Called | Default |
|---|---|---|
| `populate(run)` | at the end of `Run::new` | nothing |
| `tick(run, dt)` | in `step`, after the monsters, before separation | nothing |
| `post_tick(run)` | in `step`, after the clean-up, before the end check | nothing |
| `on_killed(run, id)` | in `kill_monster`; may end the run (`run.ended`) | nothing |
| `on_boss_hurt(run, mi)` | in `hurt_monster` for a boss monster; false = immune | true |
| `failed(run)` | in `check_end` | every hero dead |
| `debug_target(run)` | for the debug path | none (no path) |
| `boss_bar(run)` | for the snapshots | none |

- **`BossEncounter`** (`levels/boss.rs`) is the boss fight any level can include: the boss id and entity, its `BossBehaviour`, `awake`, the `arena` (hall) and its `door`. Its functions are the hook bodies: `spawn` (the boss and its extras, in the arena), `tick` (runs the behaviour once awake), `check_arena` (wake on entry, seal the door once every living hero is inside), `on_hurt` (immunity and wake-on-hit), `on_killed` (the boss's death wins the run), `debug_target` (the boss, else the arena centre) and `bar`.
- **`DungeonLevel`** (`levels/dungeon.rs`) is the room-and-corridor dungeon with an end boss. `build` picks the boss (random from the run's rng when the host chose none), generates the map with the boss's theme, and splits the `Dungeon` (`Dungeon::split`) into the shared `Layout` and its own parts (rooms, start, boss hall, door). Its hooks are the `BossEncounter` functions.
- **Pure refactor (2026-10-14):** the split changed no behaviour. The fingerprint tests `level_setup_is_unchanged` and `simulation_is_unchanged_after_waking_the_boss` pin the map, spawns, entity ids and boss per seed and 300 steps of a boss fight, recorded on the code before the split.

**Tick (`Run::step`), in order:**
1. **Players:** one queued input per tick, two if the queue holds more than 3. No input means no movement, so the server stays deterministic with respect to the client.
   - `apply_input` moves first (`collision::step_move`), then applies dash contact damage, then abilities.
   - **Knockback:** `MoveState` carries `knock_vx/knock_vy` (px/s). While they are non-zero (and the hero is not dashing), `step_move` ignores the input, moves along the knock with `Mover::Dash` (only walls stop it), then multiplies it by `KNOCK_DECAY` (e^-0.25 per 1/60 s step) and zeroes it below `KNOCK_MIN_SPEED` (8 px/s). `apply_input` skips abilities for an input that started knocked, so a pushed hero has no control at all, dash included. `Run::knock_player(pi, from, fallback_angle, dist, str)` first cuts `dist` by the hero's weight (`push_dist`, see "Who pushes"), then sets the start speed `collision::knock_speed(dist)` so the geometric slide covers it, straight away from `from`. It does nothing for dead, sinking or dashing heroes; a new push replaces an old one. Sinking and death clear it.
   - Cooldowns tick per processed input. The client does the same.
   - `terrain_player` then checks the tile under the hero's centre (not while dashing; a pushed hero slides on the ground, so a push over a chasm or deep water sinks them). A chasm or deep water starts `Player.sinking` (`FALL_TIME` 0.7 s / `DROWN_TIME` 0.9 s, `Ev::Sink`); then `kill_player` kills the hero (armour does not help) with "X fell into the abyss" / "X drowned". A sinking hero's inputs are acked but neither move nor attack. Lava calls `hurt_player(LAVA_DAMAGE)` every `LAVA_TICK` (10 per 0.5 s, the first at once), so armour and debug apply. In debug mode `kill_player` puts the hero back on `Player.last_safe` (centre of the last safe tile) instead.
2. **Monsters:** only those within 420 px of a living player run `ai::tick_monster`.
3. **Level tick** (`LevelRules::tick`): in the dungeon the boss behaviour, once the boss is awake.
4. **Separation:** overlapping monsters are pushed apart.
5. **Projectiles and hazards.**
6. **Position history:** each monster's position goes into a 32-entry ring buffer, used for lag compensation.
7. **Cleanup:** dead objects are removed, then `sweep_lights` drops the moving lights whose entity is gone and the flashes that ran out.
8. **Level post-tick and end of run** (`LevelRules::post_tick`, `check_end`): in the dungeon the boss wakes when any player enters the hall, and the entrance is sealed (DoorClosed tiles) when all living players are inside. Then the run is lost if the level's `failed` says so (default: every hero dead). Victory is set earlier, by `on_killed`.

**Combat.**
- `hurt_monster`:
  - asks the level (`on_boss_hurt`) for boss monsters: the `BossEncounter` honours `BossBehaviour::can_be_damaged` (the lich is immune while disciples live) and wakes the boss
  - makes an unaware monster search toward its attacker
  - credits damage and kills
- `kill_monster` recursively kills the monster's minions (`owner`): necromancer skeletons, summoner imps, the lich's disciples and summons. It also awards XP and coins to living players (`Player.xp`, `Player.coins`) and calls the level's `on_killed`, which sets victory if the boss died.
- **Chests and mimics.** `Run::new` turns `Layout.chests` into world objects (`ObjState::Chest`, real ones; see "World objects") and sleeping `EnemyType::Mimic` monsters. `touch_chests` (every step) opens a chest when a living player is within `CHEST_TOUCH` (12 px): `CHEST_COINS` (8–15) to every living player through `give_coins`. The same distance wakes a mimic (`wake_mimic`), as does any player hit (`hurt_monster`). A woken mimic holds still for `MIMIC_WAKE_T` (`Ai.hold`, the lid flying open), then uses the normal AI. `boss::check_arena` wakes every sleeping monster except mimics. Sleeping monsters are not pushed by `separate_monsters`.
- **Mimic gait.** `ai::gait` makes the mimic hop: it moves only while its Move animation clock is in `MIMIC_HOP_AIR` (0.2–0.7 of a 0.6 s `MIMIC_HOP_CYCLE`), at its average speed divided by that fraction. The constants go to the client through `CONST`, so `mimic.ts` draws crouch, flight and landing from the same clock (`anim_ms`). An awake mimic does not wander.
- `hurt_player` takes a `Damage`, calls `resolve`, and skips HP loss in debug mode. Death switches the player to spectating. A negative `resolve` result heals instead (see "Damage model").
- **Who pushes:** `AttackStyle::Melee` has a `knock` (px): ogre club 28, orc warrior 20, chort claw 14, everything else 0. `AttackStyle::Slam` (the ogre's ground slam) pushes every hero within its radius 24 px straight away. `ai::perform_attack` calls `knock_player` after a melee hit, with the attacker's STR. `Ranged` has no knock field, so enemy ranged attacks never push. Bosses push in their behaviours: the demon's cleave (56) and swoop (64, the user asked for "significant knockback"); the dragon's front claw (32), bite (24), tail whip (44), landing smash (36, everyone in `DRAGON_SMASH_RADIUS`) and fireball explosions (20: `Projectile.knock`, applied by `abilities::explode` to the heroes it hits). The demon's and the dragon's numbers are in `defs/bosses.rs` (`DEMON_*_KNOCK`, `DRAGON_*`). Heroes never push enemies with their own attacks; barrel blasts push them (see "Monster knockback and terrain deaths").
- **The weight rule:** every number above is the full distance. `attributes::push_dist(base, str, weight)` gives `base × min(1, (STR − weight) / 4)`, and nothing at all unless the pusher's STR is above the target's weight. Monsters push with their own STR (`Run::push_str`); bosses push with `BOSS_KNOCK_STR` (30), above every hero's weight + 4; barrel blasts use `BARREL_BLAST_STR` (18). So an ogre (weight 20) is moved by no barrel blast and not by the wolf, and the Paladin and Barbarian are pushed less than the lighter heroes.

**Damage model (`defs/damage.rs`, `defs/races.rs`).** Every hit is a `Damage { amount, split }`; there is one formula.
- **Types:** `DamageType` is `Physical 0, Cold 1, Heat 2, Magical 3, Poison 4`. The server exports the ids as `DMG_TYPE` (`generated/defs.ts`); the colours live in the client (`game/damage.ts`).
- **`DamageSplit`** gives each type a share, always summing to 1. Constructors: `physical()`, `pure(t)` and `split(&[(t, share)])`; the rest of a partial list is filled up with physical (debug builds assert that the shares stay within 1). `main_type()` is the largest share and goes into `Dmg.ty`.
- **`Resistances`** is one fraction per type (`NONE`, `of(&[...])`, `plus`). 0.5 takes half off, 1.0 is immune, above 1.0 the hit heals, below 0 is a weakness.
- **`resolve(&Damage, &Resistances) -> f64`** is the sum over the types of amount × share × (1 − resistance), with each resistance floored at −100 % (`MIN_RESISTANCE`), so a weakness at most doubles a part. A negative result means healing. Nothing else computes damage.
- **Attack splits:** melee uses the attacker's `Profile.melee`. Projectiles and effects use `kind_split(EntityKind)`: arrows and bolts physical; magic missile, shadow and gloom bolts magical; fireball 70 % heat, 20 % magical, 10 % physical; fire bolt and fire orb 70 % heat, 30 % magical; frost bolt cold; dragon fireball, breath and fire patches heat. The `Projectile` carries its `Damage`, and `abilities::explode` takes one. Lava is heat, per tick. The barrel blast is 50 % heat, 50 % physical. Falling and drowning are not damage.
- **Races** (`Race`, table in `race_def`; first guesses for the balancing pass):

| Race | Resistances | Melee split | Vision (tiles) | Darkvision (share) |
|---|---|---|---|---|
| Human | none | physical | 9 | 0 |
| Undead | physical 10 %, heat −10 %, poison 100 % | physical | 8 | 1.0 |
| Goblin, Orc, Ogre, Mimic | none | physical | 8 | 1/3 |
| Demon | magical 20 %, heat 100 %, cold −50 % | 80 % physical, 20 % heat | 9 | 1.0 |
| Dragon | magical 50 %, physical 10 % | physical | 25 | 1.0 |
| Object | physical 50 %, poison 100 % | physical | 0 | 0 |
| Elf | poison 10 % | physical | 18 | 1/3 |
| Magical Beast | poison 10 %, magical 10 % | 80 % physical, 20 % magical | 18 | 1.0 |

- **Profiles:** `races::profile(&[Race], Adjust)` adds the resistances of all listed races and the adjustment, and takes the adjustment's melee split, else the first race's. The result (`Profile { res, melee }`) is computed once at spawn and stored on every `Player`, `Monster` and `WorldObject`. Each def has a `profile()`: `classes::profile`, `enemies::profile`, `bosses::profile`, `objects::profile`. Adjustments: the wolf +20 % cold resistance (its fur); lich physical +40 % and magical +40 %; dragon heat +100 % and melee 20 % heat; demon boss magical +20 %.
- **Sight (vision and darkvision, `defs/races.rs`):** `Sight { vision, darkvision }` sits on `RaceDef`, `Adjust` and `Profile`. `vision` is a range in **tiles**; `darkvision` is a **share of vision** (0 to 1): the range at which the creature sees an unlit target. An `Adjust` can override either; the profile takes the override, else the best (highest) vision and darkvision of the listed races. Enemies set `vision` in `defs/enemies.rs` in tiles (the old pixel range / 16; every enemy overrides it, so only the darkness rule changed behaviour); bosses see 25 tiles. Heroes: `Player.sight` (from the class profile), `Player.darkvision: Option<f64>` (the debug override, `None` = the profile's) and `sight_now()` (the vision and darkvision in force now).
- **The perception rule (`run/perception.rs`):** `sees` is true when the target is within `vision`, in line of sight (`collision::line_of_sight`), and either on a lit tile (`Lights::lit`) or within `vision × darkvision`. `ai::find_visible_foe` (every enemy) and `bosses::target` use it, and the hero's snapshot filter uses the same numbers (§7). To give a creature darkvision, see §11.
- **Light refresh:** `Run::refresh_lights` rebuilds the static layer if it is dirty and casts the moving lights. It runs once per tick before the AI (so perception reads this tick's lights) and again in `send_snapshots` (positions have moved since). The test helper `Lights::fill` lights a whole map for tests that are not about darkness.
- **Who is what:** Wizard, Paladin and Barbarian plus necromancer, summoner and disciple are human; the Elven Ranger is an elf; the Dire Wolf is a magical beast; skeletons, raised skeletons and archers and the lich are undead; goblin and orc archers, orc warrior, mimic and ogre are monsters; imp, chort, summoned imp and the demon boss are demons; the dragon boss is a dragon; chests and barrels are objects.
- **Healing above 100 %:** `hurt_player` calls `heal_player` for a negative result (capped at max HP, a `Heal` event only when something was healed); `hurt_monster` heals the monster directly (a `Heal` event only when something was healed).

**World objects (`run/objects.rs`, `defs/objects.rs`).** `Run.objects: Vec<WorldObject>` holds everything on the map that is neither hero nor monster. A `WorldObject` has `id`, `kind` (an `EntityKind`; there is no separate object kind enum), `pos`, `radius`, `solid`, `res`, `gone` (removed at the end of the step) and a per-kind `ObjState`.
- **`ObjState::Chest { opened }`:** coins on touch, mimics wake nearby; `touch_chests` loops over the chest objects (skipping broken ones). Chests are not solid (heroes walk into them to open them), but a **closed chest stops shots** (`WorldObject::stops_shots`: solid, or a closed chest that is not gone), as a hidden mimic does. Its footprint `CHEST_RADIUS` (6 px) equals the mimic's radius, and the mimic has no body height, so a shot or the dagger reaches both at exactly the same distance.
- **Breaking a chest (`break_chest`):** any hit on a closed chest that `resolve` lets through smashes it (an opened chest ignores hits): it is `gone`, `Boom k 8` (`BOOM_CHEST`) shows wood splinters, and the party gets `BROKEN_CHEST_SHARE` (a third, rounded) of a fresh `CHEST_COINS` roll through `give_coins`, whoever broke it. Reason: hitting every chest once used to be a free mimic test (a real chest ignored the hit and let shots through, a mimic took damage, stopped the shot and woke).
- **`ObjState::Barrel(Barrel)`:** `fuse: Option<f64>`, `lit_at`, `igniter` (entity id of the hero who lit the chain), `vel` (slide after a push) and `sinking: Option<(time left, Sink, start)>`.
- **`hurt_object(run, oi, Damage, by)`:** calls `resolve`; a closed chest breaks (above). A barrel whose result is above 0 and that is neither lit nor sinking gets a fuse of `BARREL_FUSE` (0.3 s) and remembers `by`. Every hero attack reaches objects: shots (`advance_projectile`), `melee_arc`, `dash_contact` and `explode`. `dagger_target` returns a `DaggerTarget` (`Monster` or `Object`): the nearest monster or **closed chest** in `DAGGER_RANGE`, so standing next to a chest and attacking stabs it just as it would stab a hidden mimic; barrels and torches are not dagger targets. Enemy and boss area attacks hit objects too, with no igniter (`objects::hurt_objects_in`, built on `objects_in(run, at, r, cone)`, which mirrors `bosses::players_in`: an object counts when its centre is within `r` plus its radius, and inside the cone if one is given): the ogre slam, the dragon's landing smash, tail, claw, bite and breath pulses (the breath with the same line-of-sight check as for heroes), the demon's cleave and swoop, the lich nova and fire-patch pulses (`tick_hazards`). Single-target monster melee only hits heroes. Objects resist poison fully through the `Object` race.
- **`tick_objects`** (every step): sinking barrels count down and disappear without a blast; the others slide, check the ground (`barrel_terrain`) and burn their fuse. A barrel lit during this step by an earlier blast starts burning its fuse on the next step, so a chain advances one link per 0.3 s. No barrel explodes twice: `gone` is set first, and a lit or sinking barrel is not lit again.
- **`explode_barrel`:** sends `Boom k 7` (`BOOM_BARREL`), then hurts every hero, monster (bosses included) and barrel within `BARREL_BLAST_R` (40 px, plus the target's radius) that has line of sight to the blast, with `barrel_blast()` (30 damage, 50 % heat, 50 % physical). Heroes are pushed with `knock_player`, non-boss monsters with `knock_monster` (`BARREL_BLAST_KNOCK`, 40 px, STR `BARREL_BLAST_STR` 18), both cut by the target's weight. Damage and kill credit go to the igniter. A chain lit by an enemy shot, or by a hero who has left, still explodes and gives no credit.
- **`use_object(run, pi)`** is the one use entry point: a living, not sinking hero uses the nearest barrel (not sinking) or torch whose gap to the hero is at most `USE_REACH` (6 px); objects that are gone are skipped. `apply_input` calls it for `act`, but not for an input that started knocked. For a barrel it is `push_barrel`: slide `BARREL_PUSH` (48 px) straight away from the hero, cut by `push_dist` with the hero's STR against the barrel's weight (6; the Wizard, STR 8, moves it 24 px); for a torch it toggles it (below). Chests do nothing. Levers and the like will use the same entry.
- **Sliding barrels** move with `Mover::Dash` and the knockback decay (`KNOCK_DECAY`, `KNOCK_MIN_SPEED`). Walls, other solid objects, heroes and monsters stop them (heroes and monsters are not shoved; the body test is a square, |dx| and |dy| below the body radius plus the barrel's half size, so a barrel never ends inside a body's box). Every step the new position is rounded to the wire grid (multiples of 1/`POS_SCALE` px), so a moved barrel is always exactly representable in a snapshot and the client's predicted solids equal the server's (a 1/32 px rounding gap would exceed `move_box`'s `EPS` and let heroes snag on or walk into a pushed barrel). Dungeon barrels are placed on tile centres, which are already on the grid. `barrel_terrain`: over a chasm it falls (`Sink::Fall`, `FALL_TIME`), in deep water it sinks (`DROWN_TIME`) with no blast, in lava the fuse is set to 0 and it explodes.
- **`ObjState::Torch { wall, side, light }`:** a wall torch (`EntityKind::Torch` 82), non-solid, `Object` race, never breaks. `wall` is the wall tile it hangs on, `side` a `TorchSide` (`Face`: on a brick face with floor below; `West`/`East`: on a side wall with floor to its east/west), `light` the id of its static light (kind `Torch`), which sits on the floor tile in front of the wall (`TorchSpawn::front`), so the shadowcast starts inside the room. `spawn_torch` is called from `Run::new` for each `Layout.torches` entry, after the barrels (every other entity keeps its id) and before `add_lava_lights`. The torch is lit exactly while its light is on (`torch_on(run, light)` reads the registry; there is no copy on the object, so any `set_light` on it is seen). `set_torch(run, oi, on)` switches it by calling `set_light`.
  - **E** (`use_object`) toggles the nearest torch or barrel in reach.
  - **`hurt_object`:** a hit whose split has any `Heat` share lights the torch, any other damage that gets through its resistances puts it out. So fire shots, fire patches and barrel blasts (50 % heat) light torches; sword swings, dashes and arrows put them out.
  - **What reaches a torch:** area attacks and blasts by distance (`objects_in`, like barrels) and, in `advance_projectile`, a plain (non-exploding) shot that stops in the torch's wall tile (an exploding one reaches it by its blast).
- **Snapshots:** `objects::snap` encodes one `EntSnap` per object (anims in §4). `visibility.rs` filters objects by sight and light, like chests before; a torch (`owns_light`) is sent when in sight, lit or not.

**Light sources (`defs/lights.rs`, `run/light.rs`).** A general system: torches, lava and glowing shots are only its first users, and a new source never touches the core (see "How to add a light source", §11).
- **Kinds (`defs/lights.rs`, data only):** `LightKind` `Torch`, `Lava`, `Fire`, `Magic`, `Blast`, `Holy`, each with `radius` (tiles), default `colour` (0xRRGGBB), `intensity` (0..1, client only) and `flicker` (0..1, client only):

  | Kind (id) | Radius | Colour | Intensity | Flicker | Used by |
  |---|---|---|---|---|---|
  | `Torch` (0) | 7 | 0xffaa5a orange | 1.0 | 0.15 | wall torches |
  | `Lava` (1) | 2 | 0xff461e red | 0.8 | 0.05 | every lava tile |
  | `Fire` (2) | 4 | 0xff8c3c orange | 0.9 | 0.2 | fire shots, fire patches |
  | `Magic` (3) | 3 | 0x9678ff violet | 0.7 | 0.1 | magic shots (own colours) |
  | `Blast` (4) | 4 | 0xffb060 warm white | 1.0 | 0.3 | explosion flashes (`BLAST_FLASH` 0.4 s) |
  | `Holy` (5) | 4 | 0xffe890 pale gold | 0.9 | 0.1 | the paladin's healing wave (`HOLY_FLASH` 0.6 s, as long as its ring) |

  The radii were raised after the user's look check (torch 5, lava 1, fire 3, magic 2 before). All first guesses for the balancing pass. `kind_light(EntityKind) -> Option<(LightKind, Option<Colour>)>` is the one place that says which entity kinds carry a light from spawn: fire shots and fire patches glow orange, `Missile` violet, `FrostBolt` ice blue (0x78c8ff), `ShadowBolt` and `GloomBolt` purple (0xaa3cdc); arrows and bolts carry none. `export.rs` writes the table to `defs.ts` as `LIGHT` and `LIGHT_KIND`.
- **Registry (`Run.lights: Lights`):** `LightSource { id, kind, colour, anchor, on, expires }`. Light ids are separate from entity ids. `Anchor::Tile(x, y)` is a **static** light, `Anchor::Entity(id)` a **moving** one that follows a monster, projectile, hazard, hero or object (found by `entity_pos` in any list), and `Anchor::Point(pos)` a light on a fixed spot that is handled as a **moving** one (cast per snapshot, sent in `Snapshot.lights`, no event). `expires` (run time, `None` = never) lets the sweep remove a light by itself; flashes use it. Static or moving depends on the anchor alone, never on the kind.
- **API on `Run`** (the only way features touch light): `add_light(kind, anchor, colour: Option<Colour>) -> id` (`None` = the kind's colour), `add_flash(kind, pos, secs) -> id` (a `Point` light that expires after `secs`), `set_light(id, on)`, `set_light_colour(id, colour)`, `remove_light(id)`, `is_lit(pos) -> bool`; `Lights::get(id)` reads one source back. Changes to **static** lights send `Ev::Light`, `LightAdd` and `LightRemove` (§4); a static light added while the run is built (`tick == 0`) sends nothing and goes out in `RunStartInfo.lights`. A moving light never sends an event: its position travels in `Snapshot.lights`.
- **Static layer:** `Lights` keeps one `bool` per tile. Each lit static source runs `fov.rs` shadowcasting from its tile with its kind's radius and ORs the result in; opaque tiles stop the light but are lit themselves, as with sight. Any add, remove, switch or map change sets a `dirty` flag (`mark_dirty`), and `refresh` rebuilds the layer lazily on the next query (visibility calls it once per snapshot round). Cost: one shadowcast per static source, only after a change.
- **Moving layer:** `moving_lights()` lists every lit `Entity` source at its entity's current position and every lit `Point` source at its spot (`Lit { pos, tile, kind, colour }`). A moving light lights exactly what a static light on its tile would: the radius-r shadowcast from `tile`, in the same square window. `tile` is `light_tile(pos)`, the tile of the position **as the snapshot sends it** (f32, then 1/`POS_SCALE` px), so the client, which only has that position, casts from the same tile. `Lights::cast_moving(map, &moving)` marks those tiles in a second per-tile layer (it clears only the tiles it set last time); `send_snapshots` calls it once per snapshot round. Only a few moving lights exist at a time, so this stays cheap. `Lit::reach()` ((radius + 1) tiles) is only used by the moving-light list (§7).
- **`is_lit(pos)`:** the tile of `pos` is in the static or the moving layer (`Lights::lit`); it refreshes both first. One rule for every light, on both sides: a tile the server counts as lit is the tile the client draws lit.
- **Attaching and the sweep:** `attach_kind_light(id, kind)` adds the light `kind_light` names; the spawn paths of projectiles and hazards call it (a shot that dies in its first step gets none). `sweep_lights` (after the step's cleanup) drops moving lights whose entity no longer exists, so no despawn path can leak one, and every light whose `expires` time has come.
- **Explosions flash:** `abilities::explode` (every projectile with an explosion radius: the hero's fireball, the dragon's fireballs) and `objects::explode_barrel` call `add_flash(LightKind::Blast, pos, BLAST_FLASH)`, so an explosion lights its surroundings for 0.4 s, also where it is dark. The flash is flat (full strength until it expires; the client's flicker wobbles it): a fade-out would need its age or a scale on the wire. The paladin's healing wave flashes too: `try_use` (`AbilityId::Heal`) adds a `Holy` flash for `HOLY_FLASH` 0.6 s on the paladin's spot. Other `Boom` events are not explosions and get none (ogre and dragon shockwaves, lich nova, the demon's ring burst, whose fire orbs carry their own light). The demon's fire orbs do not explode.
- **Lava:** `add_lava_lights` (in `Run::new`, after the torches) puts a static `Lava` light on every lava tile. `Run::set_tile` is the way to change a tile mid-run: it sends `Ev::Tile`, keeps the lava lights in step (add or remove, with events) and marks the light map dirty (a door or wall changes what light reaches).
- **Numbers** (`defs/objects.rs`, all first guesses): radius 6 (a 12 px square), fuse 0.3 s, blast radius 40 px, blast damage 30, blast push 40 px, push 48 px, use reach 6 px.

**Status effects (`defs/effects.rs`, `run/effects.rs`).** A general system: blind, sleep, petrified, slowed, accelerated, the damage-type effects (burning, frozen, poisoned and their lower tiers chilled, singed, tainted) and entangled, fear, warded and coated are only its first rows, and a new effect never touches the core (see "How to add an effect", §11). Data and runtime are split like the lights.
- **Data (`defs/effects.rs`).** `EffectKind` is an open set; its `u8` id is the effect's bit in the snapshot (`Blind` 0, `Sleep` 1, `Petrified` 2, `Slowed` 3, `Accelerated` 4, `Burning` 5, `Frozen` 6, `Poisoned` 7, `Chilled` 8, `Singed` 9, `Tainted` 10, `Entangled` 11, `Fear` 12, `Warded` 13, `Coated` 14; `COUNT` 15, so 15 of the 16 bits of the `u16` mask are used; `ALL`, `bit()`). `def(kind)` returns an `EffectDef`: default `duration` (s; a source may pass its own), `positive` (the HUD frame is green instead of red), `mods: &[StatMod]` and the flags `no_move`, `no_act`, `no_turn`, `prone` (lying down), `wakes_on_damage` (no effect uses it yet), `wakes_on_use` (a teammate's E ends it), `dot: Option<(DamageType, f64)>` (damage over time, see below), `resisted_by: Option<DamageType>` (a damage-type effect is refused by that type's resistance), `replaces` (the weaker tier it removes), `cancels` (kinds removed instead), `ends_in_water`, `save: Option<Attr>` (the Attribute that shortens it: STR for Entangled, WIL for Fear; `None` means WIL for a magical source, else CON) and `flees` (Fear: the creature runs from the effect's source and cannot attack). A `StatMod` is a `Stat` (`MoveSpeed` factor, `Vision` in tiles, `Darkvision` share, `Resist(DamageType)`, `KnockTaken` factor), an `Op` (`Add`, `Mul`, `Set`) and a value.
- **Today's rows:** Blind (3 s) sets vision and darkvision to 0. Sleep (4 s) multiplies vision by 0.15 and sets `no_move`, `no_act`, `prone`, `wakes_on_use`. Petrified (3 s) adds 0.75 to Physical and 0.5 to Cold, Heat, Magical and Poison resistance, takes 0.4 of knockback, and sets `no_move`, `no_act`, `no_turn`. Slowed (3 s) multiplies move speed by 0.5, Accelerated (3 s, `positive`) by 1.5. Burning (3 s, `dot` heat 6 per second, `ends_in_water`, cancels Frozen), Frozen (2 s, `dot` cold 4 per second, `no_move`, `no_act`, `no_turn`, cancels Burning) and Poisoned (4 s, `dot` poison 4 per second) are the damage-type effect rows. **Plan 3b rows:** Chilled (3 s, move speed x 0.7, cancels Burning and Singed), Singed (3 s, `dot` heat 3 per second, `ends_in_water`, cancels Frozen and Chilled) and Tainted (3 s, `dot` poison 2 per second) are the lower tiers (see below). Entangled (3 s, `no_move`, save STR; it does not stop attacking or turning), Fear (3 s, `flees`, save WIL; the creature cannot attack), Warded (positive, 3 s: effect resistance +1.0 to Blind, Sleep and Petrified) and Coated (positive, 3 s: only a marker, the hero's weapon attacks read it, see Poison Coat in §11a). Undead resist Fear 1.0 and demons 0.5 (race effect resistances); the bosses resist it fully (the demon through its race plus 0.5, the dragon 1.0, the lich 1.0).
- **Damage-type effects and damage over time.** An effect with a `dot` (a `DamageType` and damage per second) hurts its creature in `tick_effects`: every `DOT_TICK` (0.5 s) one hit of `rate * DOT_TICK`, built with `Damage::effect_tick`. That damage has `Damage.from_effect` set, and `hurt_player` and `hurt_monster` skip every effect step for it (no wake, no `OnHit`, no damage-type effect), so a burn never refreshes itself. It still goes through the creature's resistance, so a creature that resists the type takes less. The table is `TYPE_EFFECTS` (six rows of type, least share and effect: Heat 0.5 Burning and 0.25 Singed, Cold 0.5 Frozen and 0.25 Chilled, Poison 0.5 Poisoned and 0.25 Tainted; tests check it against each def's `resisted_by`): after a normal hit, `type_effect_hit` applies, for every damage type in the split, the highest tier its share meets (`type_effects`): at least `TYPE_EFFECT_SHARE` (0.5) gives Burning, Frozen or Poisoned, at least `TYPE_EFFECT_LOW` (0.25) gives Chilled, Singed or Tainted, so a fireball (70 % heat) and a barrel blast (exactly 50 %) burn, a hit with 30 % heat singes, a claw with a fifth of heat does nothing, and lava burns through the same rule. There is no chance anywhere: an effect is always applied, and only the target's save and resistance shorten or refuse it. **Tiers:** a stronger tier replaces the weaker one of its type (`replaces`; applying Burning removes Singed) and the weaker is refused while the stronger is on; heat and cold cancel across tiers (`cancels`: Burning and Singed remove Frozen and Chilled, and the other way round). **Power:** share-driven effects use power `max(10, governing)` (`TYPE_EFFECT_POWER` 10 is the floor), so the Staff of Rot, wielded with STR 8, poisons at power 10, not 8. **Resisted by its type only:** a damage-type effect has no effect resistance of its own. `apply` refuses it when the creature resists its `resisted_by` type at 1.0 or more (through its other effects too), so demons and the dragon never burn, undead are never poisoned, and a petrified creature with half heat resistance does not burn; a partial resistance lowers each tick's damage and does not shorten the effect. **Cancels:** applying an effect that `cancels` one the creature has removes that one and does not apply the new one (fire thaws Frozen, cold puts out Burning). The cancel runs before the save and the resistance checks, so even a resisted effect cancels (the user, 2026-10-19): fire still thaws a frozen creature that resists heat completely or stands in water. **Water:** at the top of each tick, a creature standing in shallow or deep water loses every effect with `ends_in_water` (Burning). **Credit:** a burn that kills a monster counts as a kill for `last_hit_by`, the last hero who hit it. The burn damage itself is also added to that hero's damage total (bounds-checked, like the kill credit). **Water refusal:** `apply_effect` also refuses an effect with `ends_in_water` while the creature's centre is on shallow or deep water, so a fire hit on a hero standing in water sends no Effect on/off pair.
- **Resolution (`resolve_stat(base, stat, kinds)`).** All `Add`s, then all `Mul`s, then the lowest `Set`, so a `Set` beats the rest (blind and asleep together see 0). **The resistance cap:** an effect never lifts a resistance above 1 (immunity) unless the base already is above it, so undead stay exactly immune to poison under Petrified instead of turning it into healing, and an existing heal stays as it was.
- **Effect resistances.** One system: every effect that is not a damage-type effect is resisted by an effect resistance, a fraction per kind in `EffectResistances` (`NONE`, `of`, `get`, `set`, `plus`, shaped like `Resistances`; a slot per kind, so a new effect has one at 0). `effect_secs(secs, r)` gives `secs × (1 − r)`, `None` (refused) at `r >= 1`; a negative `r` lengthens, floored at `MIN_RESISTANCE` (−1, at most double). It applies after the save (§11a), to positive effects too (the dragon's Accelerated is halved). The resistances sit next to the damage ones: `RaceDef.effect_res`, `Adjust.effect_res`, summed into `Profile.effect_res` by `races::profile`; heroes read `Sheet.effect_res`, monsters `Monster.effect_res`, and effects can change them through `Stat::ResistEffect(kind)` (`Effects::effect_res(base)`, capped like `Resist`). Today's values: Elf and Magical Beast Sleep 1.0 (so the Elven Ranger and her wolf), and the bosses in their `Adjust` (`defs/bosses.rs` `profile`): every boss Sleep 1.0; the lich Blind 1.0 and Petrified 0.5; the dragon Blind, Petrified, Slowed and Accelerated 0.5. A test checks that nothing sets an effect resistance for a damage-type effect.
- **Runtime (`run/effects.rs`).** `Effects` is a small list of `ActiveEffect { kind, left }` on every `Player` and `Monster`, with the stats resolved through it: `speed_mul()`, `sight(base)`, `res(base)`, `effect_res(base)`, `knock_taken()`, `no_move()`, `no_act()`, `no_turn()`, `bits()`. Adding a kind that is already on keeps the longer time and sends no second event. The API other code uses is on `Run` and takes a `Creature` (`Player(i)` or `Monster(i)`): `apply_effect_from(c, kind, secs, power, magical)` (the API for hits: scales a harmful effect's time by the target's save, see §11a, then calls `apply_effect`) and `apply_effect(c, kind, secs: Option<f64>)` (unscaled: applies the effect resistance, refuses the dead and sinking, returns whether the effect is on; for debug and tests), `remove_effect`, `has_effect`, `hit_effect(c, OnHit)` and `wake_teammate`. `tick_effects` runs first in every step (timers count down; the dead and sinking lose everything) and `damage_wakes` after a hit that does damage.
- **Hits carry effects.** `Damage` has `on_hit: Option<OnHit>` (`Damage::with_effect`); `OnHit { kind, secs, magical, power, look }` is always applied (the `chance` field and its rolls were removed in plan 3b; the fingerprints did not change). `hurt_player` and `hurt_monster` apply it after the damage, also when the hit did none (a pure effect hit shows no number and no flash). `defs/enemies.rs::on_hit` and `defs/abilities.rs::on_hit` are the hooks for a monster's or a hero ability's effect; both return `None` today (hero abilities get theirs from weapons, `own.effect` and the Staff of Rot's 50 % poison share).
- **`Apply`, looks, sources and saves (`run/effects.rs`).** `Apply { kind, secs, power, magical, look, source }` is the one description every source builds (`Apply::plain`, `Apply::from_hit(OnHit)`), and `Run::apply(c, Apply)` is the one path: cancel, refuse when a stronger tier is on, scale by the save (the effect's own `save`, else WIL or CON), then the effect resistance, water and the time, add, remove the weaker tiers. `apply_effect` and `apply_effect_from` are thin wrappers. An `ActiveEffect` also keeps its `look`, its `source` (the id and position of whoever applied it) and `from`. A refresh keeps the longer time and takes the new look and source. **Looks (`EffectLook`):** `Plain` (0) or `Vines` (1) says how the effect is drawn, chosen by the source (Entangle: Vines); the client reads it from the snapshot (below). **Fear** (`flees`): a creature with it runs from `fear_from`, the source's live position while the source is at least 1 px away, else the last known spot; it does not attack (`ai::flee`, called in `run/mod.rs` after `no_act` and before the ally check; no rng, and it moves by `gait()`, so a frightened mimic hops). A frightened monster on a blocked tile still skips `escape_terrain`.
- **Where the flags and stats are enforced.** `no_move`, `no_turn`, `no_act` and `speed_mul` for heroes in `apply_input` (`run/mod.rs`); `speed_mul` for monsters in `ai.rs`; `no_act` for monsters at the top of their turn (`run/mod.rs`) and for a boss encounter in `levels/boss.rs` (a petrified boss is frozen). `res` in `hurt_player` and `hurt_monster`, `knock_taken` in both knockback functions. `sight` through `sight_now` on `Player` and `Monster`, so `perception::sees`, the snapshot filter and the `SelfW` vision all use the effect's vision.
- **The lich** (`run/bosses/lich.rs`) casts three spells from its `SPELLS` table (`Gaze`, `Sleep`, `Blind`, tried in that order when their cooldown is up and a hero it sees does not already suffer the effect; delete an entry to balance). Blind: a dark orb (`EntityKind::BlindOrb` 61) that does 6 damage and blinds for 3 s. Sleep: a purple orb (`SleepOrb` 62) that puts a hero to sleep for 4 s. Gaze (`Anim::Gaze` 14): a 1 s wind-up locked on one hero, and if the lich still sees that hero when it ends, the hero is petrified for 3 s. The orbs fly at `LICH_ORB_SPEED` 90 px/s. All the numbers are `LICH_*` in `defs/bosses.rs` (first casts at 4, 7 and 9 s, cooldowns 10, 14 and 18 s).
- **Wire.** `EntSnap` has a trailing `u16` bitmask `effects` (creatures only). The own hero also gets `SelfW` elements 14 to 17: `vision` (tiles, through the effects), `effects` (`[id, seconds left]` pairs), `speed_mul` and `no_act`. `Ev::Effect{id, kind, on, look}` (wire code 13; `look` is the effect's look on a start and 0 on an end) says an effect started or ended on an entity; the client does not read the event's look (see Client); for a hero it is an `event_on_hero`, for a monster it is FOV-filtered. `ClientMsg::DebugEffect{kind}` (F8) is honoured only when debug is allowed and marks the run as debug. **Looks on the wire:** the snapshot has a tenth element `looks` (`SnapW`), a list of `[entity id, effect id, look]` for the entities in view that carry a non-plain look (`visibility::looks_of`, players and monsters); the client reads looks from snapshots only, so it covers both a start and a late view (the user ruled, 2026-10-21: `Ev::Effect.look` stays on the wire but is unused client-side). The `EffectLook` table is exported as `EFFECT_LOOK`, and `flees` per effect in `EFFECTS`.
- **Waking.** E next to a teammate with a `wakes_on_use` effect ends it (`wake_teammate`, within `USE_REACH`); waking beats using an object. The mimic's old `ASLEEP` flag became `dormant` and is now `hiding` (see "Hiding and dormant"), so "asleep" means the effect only.
- **Client (`game/status.ts`, `anim/EntityView.ts`).** `has(bits, kind)`, `lyingPose` and `lieLayout` (a prone figure lies rotated 90° towards its facing, the floor side cropped), `frameBounds`, and `StatusView`, the marks around one figure, owned by its `EntityView`: blind (three dark motes circling the head), asleep (a rising "z" and the lying pose), accelerated (fading afterimages), burning (three flickering flames that hop around the body), frozen (a blue additive haze and snowflakes that fade in and out), poisoned (a green tint that pulses, and bubbles rising), chilled (a pale blue body tint, legs at 0.7 pace, an occasional snowflake), singed (small rising embers), tainted (a slow faint green pulse, 0.3 at most against Poisoned's 1.0), fear (a bobbing "!" above the head in the sound-text style), coated (a green glint at the hand, `StatusAnchor.hand`), entangled (bands at the feet; a `Record<Look, ...>` table, so a new look fails to compile) and warded (a thin pulsing gold ellipse). `lookOf(looks, id, effect)` (in the Phaser-free `game/looks.ts`) reads a look from a snapshot's `looks` (`Plain` when absent); the `Interpolator` sets `EntState.entangled` from the same snapshot that supplies the entity's `effects`, so the look never runs ahead of the effect. `EntityView` itself draws petrified (greyscale on body and weapon, frozen on the frame it was turned to stone in; WebGL only) and slowed (a blue tint, legs at half pace); frozen also holds the animation frame and the weapon pose it started on (no greyscale). `Predictor` takes `speedMul`, `noAct` and the no-turn flag from `me`; `LightView` takes its vision from `me.vision` instead of a constant; the lich's gaze is a thin grey beam drawn while `ANIM.Gaze` shows (`GameScene.drawGaze`). Hints: "E Wake" over a sleeping teammate and "Asleep. A teammate can wake you" with an E key cap (the first is the board's `KeyCap`, the second `Hud.setAsleep`). HUD icons (`ui/hud.ts`; one drawn symbol per kind in `ui/effectIcons.ts` `EFFECT_ICON`, see §9 "UI"): the own hero's with the whole seconds left, the party's without; the other heroes' also sit beside their name tags (`game/tagEffects.ts`). `?gallery` has a row per effect and `?lich` shows the three spells.

**Hiding and dormant.** Two waiting states of a `Monster`, both skipped by the AI until they end. `dormant` (`FLAG.DORMANT`): the boss before the party enters its hall, the lich's channelling disciples. `hiding` (`FLAG.HIDING`): a mimic that looks like a closed chest; `touch_chests` or a hit ends it. Heroes sense neither; the wolf growls at `hiding` ones (never at dormant ones) and bites neither. A later concealed creature (an invisibility effect, a ghost) would use `hiding` and decide itself whether the wolf senses it. (The Assassin's Hide ability and `flags::HIDDEN` are gone; Hide may come back as an invisibility effect.)

**Companions (`run/companion.rs`, `defs/companions.rs`; the Elven Ranger's Dire Wolf).** The first allied creature is an ordinary `Monster` with `ally: Some(Ally)` (`Monster.is_ally()`), so it reuses movement, terrain, knockback, effects, lights and snapshots. `Ally` holds the owner's hero id, the growl state, the dash and its cooldown, the last safe tile and the leash timers. `Player.wolf` holds the wolf's id. The numbers are in `defs/companions.rs` (`WOLF_*`); its profile is a Magical Beast plus 20 % cold resistance (`wolf_profile`).
- **Ability.** `AbilityId::SummonWolf` (secondary, 8 s) calls `companion::use_ability`: no living wolf means `spawn_wolf` (beside the ranger, `spot_beside`, `Boom k 9`); a living one means `heal_monster` for 20 % of its max (also at full health). `wolf_died` (called by `kill_monster`) gives no XP and no coins, sends `Ev::Died` and the message "<name>'s wolf has fallen" and sets the ranger's `cd2` to 60 s (divided by attack speed). `vanish_orphans` removes a wolf whose owner is no longer alive (fallen or left) with a puff, no message and no cooldown.
- **Tick (`tick_wolf`, from `Run::step` instead of the enemy AI; not while pushed, sinking, asleep or frozen).** Reappear beside the ranger beyond 12 tiles or when no path exists (checked every 0.5 s; this covers the sealed boss hall); the dash and bite on prey (`find_prey`: enemies it sees within 3 tiles of the ranger or 1.5 of the wolf, and within the 6-tile leash of the ranger, nearest to the ranger first; never dormant, hiding or flying ones); the growl; following (starts beyond 2 tiles, stops inside 20 px). The dash (4 tiles, 300 px/s, 20 damage, 5 s) jumps chasms; an attack dash that would end over a chasm carries on to solid ground, and `dash_back` returns to `last_safe` after a push over a chasm (it falls only with the dash on cooldown). Hits on prey go through `hurt_monster` with the ranger as source, so kills and statistics count as the ranger's.
- **Growl (`tick_growl`).** The wolf's own `perception::sees` (18 tiles, full darkvision, walls block) finds awake and hiding enemies it has not growled at; at most one growl every 4 s; it steps 24 px toward the enemy (inside the leash, on walkable ground) and sends `Ev::Growl { id }` to the whole party without a position. The enemy is not revealed. The client draws "grrrr" (sound text, §7) and shakes the figure.
- **Foes.** Enemies choose among heroes and allies: `ai::find_visible_foe` (heroes and allies the monster sees) yields `Target::Player` or `Target::Ally(id)`. Area attacks and hazards use `Run::foes_in` and `foes_touching` (heroes first, then allies), `hurt_creature` and `knock_creature`, so bosses' cleaves, breath, novae, fire patches and barrel blasts hit the wolf; bosses and the lich's curses still choose heroes. `hurt_monster` refuses damage from a hero source on an ally, which is the safety net behind the per-attack skips (`dagger_target`, `melee_arc`, `dash_contact`, `advance_projectile`, `explode`); each has a test. Holy Light heals allies in range.
- **Snapshots.** Allies are always sent to the party (like heroes, `snapshot_ents`), with `extra` = the owner's id and a health bar; the client draws their numbers and bar by the hero rule (over the darkness, see Draw order). `Ev::Dmg` and `Ev::Heal` on an ally have `p` set (the hero rule).
- **Client.** `isAllyKind` (`anim/defs.ts`), `FIGURES[DireWolf]` (atlas frames `dire_wolf_idle_anim_f0-3`/`dire_wolf_run_anim_f0-3`, trimmed from the 32×32 canvases by `build-atlas.ts`; the union box is 30×19 px), a lunge for the bite, the `Growl` handler with the shake, `natureSparkles` for `Boom k 9`, `secondaryLabel` in `ui/hud.ts` ("Summon Wolf" or "Heal Wolf", from `FrameStats.wolf`: the party's wolf entity with the own id as `extra`), prediction of the cooldown only, and the cosmetic dagger and shot checks skip allies.
- **Adding another companion** means a new `EntityKind`, a profile, an `Ally` behaviour in `companion.rs` and its own ability arm; the foe layer, snapshots and client allies need nothing new.

**Solid objects in movement (`collision.rs`).** `move_box` and `step_move` take `solids: &[Solid]` (`Solid { x, y, half }`, squares). Solids are checked axis by axis like tiles; a figure that already overlaps one may still move away from it in any direction, so nobody gets trapped. `Run::solids(except)` lists the objects for which `WorldObject::blocks()` holds (solid, not gone, not a sinking barrel). The same predicate decides whether a shot stops at an object (`advance_projectile`, through `stops_shots`, which adds closed chests), which tiles A* avoids (`Run::object_tiles`) and whether a straight walk is clear (`ai::object_free_line`), so a sinking barrel stops nothing. They apply to heroes (`apply_input`), monsters (`ai::move_toward`, `separate_monsters`, `slide_monster`) and sliding barrels. The TypeScript port (`sim/collision.ts`) has the same parameter, and the predictor (`world.ts`, `Predictor.solids`) takes the barrel positions from the latest snapshot (`GameScene` keeps those with `anim < 2`). The shared fixtures include runs with barrels, so `sim.test.ts` pins Rust and TypeScript to the same result. Barrels do not block sight.

**Monster knockback and terrain deaths (`run/mod.rs`).**
- `Monster` has `knock` (px/s), `sinking`, `burn_t` and `last_hit_by`. `knock_monster(mi, from, dist, str)` pushes a monster by weight (`push_dist`) straight away; bosses, airborne and sinking monsters are never pushed. A pushed monster slides (`slide_monster`: `Mover::Dash`, so only walls and solids stop it) and its own movement is skipped meanwhile.
- `terrain_monster` runs after the AI step, like `terrain_player`. A monster over a chasm or deep water starts sinking (`FALL_TIME` / `DROWN_TIME`, `Ev::Sink` with the monster's id, wind-up cleared); when the time is up, `kill_monster` runs once, with the kill credited to `last_hit_by`. Bosses are skipped. Lava burns monsters that are not lava walkers (`Mover::Demon`) with heat damage `LAVA_DAMAGE` every `LAVA_TICK`; a lava death gives no kill credit, but a burn tick (Burning, `from_effect` damage) that finishes a monster credits `last_hit_by`. A monster standing on ground it cannot walk (lava) walks out first (`ai::escape_terrain`, ignoring heroes). The client reuses the hero fall and drown animations for monster figures.
- Known gaps (deferred): `escape_terrain` has no fallback when no walkable tile lies within 3 tiles, so such a monster stays put; a wind-up is not cleared by `knock_monster` (only by sinking), so an attack may resume after the slide.

**Lag compensation.**
- Melee arcs, the dagger and dash contact test monster positions rewound by the client's `view_lag` (RTT/2 + its interpolation delay), up to 31 ticks.
- Player projectiles spawn fast-forwarded by RTT/2, at most 150 ms, through the same 4 px hit-checked steps as every tick (`advance_projectile`), so the fast-forward cannot skip an enemy. Every shot ends at the first wall or figure it meets: hero shots never pass through enemies (an explosion still hits everyone in its radius).
- **Shot hitboxes:** player projectiles hit a monster when `Monster::shot_dist` is below its radius plus the shot's. Shots are drawn `SHOT_HEIGHT` (8) px above their ground point and figures stand up from their feet, so the hitbox is a capsule from the feet north to `EntityKind::body_height` (sprite height above the feet, measured from the atlas) minus `SHOT_HEIGHT` and the radius, plus the dragon's lift while airborne. Small figures stay (nearly) round; the demon is hit up to its horns. Movement, melee and explosions still use the round footprint.

**AI (`ai.rs`).**
- **Wide figures:** `path_toward` (also used by the bosses' chase since boss halls have chasms) treats figures wider than a tile (the demon, the dragon) specially: the straight-line shortcut also checks lines offset by their radius against terrain (`collision::terrain_line`; walls are fine, figures slide along them), A* (`astar_clear`) charges extra for tiles next to anything they cannot enter, a waypoint they make no progress toward is skipped, and a boss with no path walks straight at the hero. The swoop still charges in a straight line and stops at a chasm edge.
- **Movers:** each monster has a `mover`: `Mover::Demon` for imps, chorts, summoners, summoned imps and the demon boss, `Mover::Enemy` otherwise. `move_toward`, `separate_monsters`, `astar` and summon spots use the walking rule for it, and `path_toward` only walks straight when `walk_line` (not just line of sight) is clear. So enemies never enter chasms or deep water, and only demons cross lava. The debug path to the boss is planned as `Mover::Enemy`, around all terrain.
- **Targets:** `Ai.target` is `Option<Target>`, `Target::Player(id) | Object(id) | Place(Vec2)`. Perception sets `Player` every tick. The barrel an enemy aims at lives in its `Windup` (`Windup.at: Option<Target>`), because perception would overwrite `ai.target`. `Place` has no user yet.
- **Enemies shoot barrels:** before a ranged attack of a non-boss enemy (`ai::barrel_near`), it looks for an unlit, resting barrel that it can see, within its range, within the blast radius of its target hero, and far enough from itself that the blast spares it (blast radius + its own radius + 8 px). It picks the one closest to the hero and winds up toward it. When the wind-up ends, it shoots the barrel if it is still there and unlit, else the hero. Bosses and melee enemies never do. Enemy shots stop at a barrel and hurt it.
- **Pathing around barrels (beyond the plan, added because big bosses got stuck):** `path_toward` walks straight only when `object_free_line` is clear, i.e. no solid object within the body's radius plus 6 px of the line. Otherwise it runs A* (`astar_clear`) with the tiles under resting barrels blocked (`Run::object_tiles`) and an extra cost of 8 for tiles next to a barrel (the "squeeze" cost; it applies to all monsters). So a chaser switches to A*, refreshed every 0.6 s, whenever a hero stands next to a barrel; that costs a little CPU and can make chasers slightly late there. Sinking barrels do not count (`WorldObject::blocks`).
- Perception: the nearest living hero or ally (the wolf) within `sight` and with line of sight. Enemies never target players they cannot currently see.
- States: `Idle` (wander near home) → `Chase` (melee approach, ranged keep a preferred distance) → wind-up → attack. Losing sight leads to `Search` (A* to last known position) and then `Return` (A* home).
- Wind-ups telegraph attacks: the client flashes the body red and shakes it. The hit lands only if the target is still seen.
- Necromancers raise up to 3 skeletons (cooldown 7 s); summoners summon imps (`SummonedImp`, drawn as a normal imp) the same way. `Ev::Raise.k` tells the client which effect to draw (0 green, 1 fire, 2 the lich's dark purple).
- **Ogre (mini-boss):** `EnemyType::Ogre` (`KIND.Ogre` 22), radius 10 (wide, so its chase uses `path_toward` with clearance like the bosses instead of `move_toward`), 260 HP, slow. Main attack: club (`Melee`, knock 28). Alt: `AttackStyle::Slam{radius, damage, cooldown, windup, knock}`, chosen when two living heroes' centres are within `OGRE_SLAM_RADIUS` (34 px), or one while the club is on cooldown. Its wind-up uses `Anim::Slam` (10); the client draws the telegraph ring from `animT` and `CONST.OGRE_SLAM_RADIUS`/`OGRE_SLAM_WINDUP`. - **Demon dungeon:** `enemies::for_boss` (through `Level::enemy_type`) swaps types when `Run::new` spawns the dungeon's enemies: with the demon as boss, skeleton archers become imps, skeleton warriors chorts and necromancers summoners. - Minions are never tinted: raised skeletons and summoned imps look like the ordinary ones (the user's request).

## 6. Dungeon generation (`dungeon/generate.rs`)

The map is 140×140 tiles of 16 px. Tile ids: Void 0, Floor 1, Wall 2, DoorOpen 3, DoorClosed 4, ShallowWater 5, DeepWater 6, Chasm 7, Lava 8.

**Tile rules (`dungeon/mod.rs`, mirrored in `client/src/sim/map.ts`).** There is no single "solid" rule any more:
- `opaque`: Void, Wall and DoorClosed. Blocks sight (FOV, `line_of_sight`) and projectiles. Terrain is never opaque.
- `blocks(x, y, mover)`: opaque tiles block everyone. Deep water blocks every mover but `Dash`; chasms block `Enemy` and `Demon` (heroes may step in, and fall); lava blocks only `Enemy`.
- `speed_factor(pos, mover)`: `SHALLOW_SPEED` 0.7, `LAVA_SPEED` 0.4 (1 for demons), 1 for a dash. `step_move` takes it from the tile under the hero's centre at the start of the step.
- `safe`: Floor, DoorOpen and ShallowWater, the ground a hero can stand on unharmed. Generator reachability (`bfs`) and `last_safe` use it.

The generator is seeded (ChaCha8) and deterministic:
1. **Placement:** built in a canonical orientation. The start room (8×8) is at the bottom center and the boss hall (26×20) at the top center. Rooms (6–10) and halls (12–18 × 11–15) are rejection-sampled below a band that keeps them away from the hall.
2. **Connections:**
   - a minimum spanning tree plus up to 6 extra loop edges, carved as 3-wide L corridors
   - the boss hall gets a single corridor with a 3-tile entrance (DoorOpen tiles, sealed later)
   - one-tile wall stubs left by overlapping carves (a cell with floor on three sides and around both corners between them) are filled with floor; they would draw as T junctions, and filling them opens no new path
   - walls are placed on every void cell next to floor
3. **Validation, retried on failure:** every room is reachable (BFS), and the boss hall is the farthest area by path distance, with a margin of 4 tiles.
4. **Population:** enemies scale with path depth. Necromancers appear only in halls.
   **Chests:** `place_chests` gives about one in three rooms and halls a chest on its top row (enemies never spawn there), against the wall, with floor on both sides and below so it never blocks a corridor mouth. A quarter are mimics. Chests use their own random stream (a clone of the generator rng on stream 7), so adding them did not change the maps of existing seeds.
5. **Terrain:** `place_terrain` runs on its own stream (8), like the chests. The theme (`Theme::for_boss`: lava for the demon, water otherwise) is passed into `generate(seed, theme)`; `DungeonLevel::build` picks the boss before generating. In ordinary rooms (40 %) and halls (two tries at 60 %) it places:
   - **pools:** ovals a tile away from the walls. Water pools are deep wherever all 8 neighbours are pool, so a shallow rim always surrounds the deep centre; lava pools are all lava
   - **chasm strips:** wall to wall across the room, 1 to `MAX_CHASM` (3) tiles wide so the Barbarian's dash clears them, with a 2–3 tile floor bridge

   A feature only covers floor, keeps two tiles from corridor mouths (open ground outside the room) and never covers a chest. It is undone if it cuts any safe ground off from the start or makes a room as far as the boss hall. Enemy spawns it covers move to the nearest free floor tile in the room. The start room stays clear. About 4 % of the floor becomes terrain.

   **Boss hall chasms** (`place_boss_chasms`, stream 9, every theme), so knockback matters in boss fights: one or two **wall strips** (4–7 tiles long, 1–2 deep, along any wall) and one or two **pits** (2x2 to 3x2, three tiles from the walls). Nothing goes within 3 tiles of the boss's start or near the entrance (the bottom centre, 4 tiles to each side, 5 deep). Pits keep 3 tiles from other chasms (the dragon is over two tiles wide), strips 2. A feature that cuts any hall floor off from the entrance is undone.
   **Lava pool in the demon's hall** (`place_boss_lava`, after the chasms on the same stream, lava theme only, asked for by the user): one oval lava pool (as in the rooms, 4×4 to 7×6), kept off the boss's start and the entrance like the chasms, with a tile of floor between it and any chasm, and undone if it cuts hall floor off from the entrance (up to 100 tries). The demon crosses it unharmed and at full speed (`Mover::Demon`); heroes knocked in are slowed and burn.
   **The ogre** (`place_ogre`, stream 10, after the terrain): one per dungeon, in a random ordinary room or hall at depth ≥ 0.35 (any ordinary room if none fits), on a tile with safe ground in all 8 neighbours and no chest. It is pushed to `spawns`, so it rotates with them. Stream 10 is a clone, so maps, spawns and chests of existing seeds are unchanged.
   **Barrels** (`place_barrels`, stream 11, last, a clone of the generator rng, so the maps, spawns, chests, terrain and ogre of existing seeds are unchanged): about one in four ordinary rooms and halls (at least 6×6) gets a group of 2–4 barrels in a 2×2 block, away from the walls, on tiles with plain floor all around (no wall, door, water, chasm or lava next to them), and not within a tile of an enemy spawn, a chest or another group. The boss hall gets 3–5 single barrels, each with a 7×7 area of plain floor around it (so a wide boss can always pass), outside `hall_keep_clear` (the boss's start and the entrance) and at least 4 tiles from the next barrel. A barrel or group is only placed if, with its tiles counted as walls, no safe tile is cut off from the start that was reachable before. With few valid spots a hall can get fewer than three barrels (best effort). They end up in `Layout.barrels`, and `Run::new` spawns them as objects.
6. **Rotation:** a random quarter turn, so the start can be on any side and the boss hall is on the opposite side.
7. **Torches** (`place_torches`, stream 12, **after** the rotation, so a "face" is a brick face on screen; a clone of the generator rng, so the maps, spawns, chests, terrain, ogre and barrels of existing seeds are unchanged; `level_setup_is_unchanged` leaves torches and their ids out):
   - **Candidates:** a wall cell with floor directly below and no floor left or right (`Face`), or with wall above and below and floor to one side (`West`/`East`, side sconces). Doorway jambs and corners never qualify (the "no floor left or right" test on `Face` is what rules out jambs).
   - **Spacing:** each straight run of candidate cells (per room or corridor stretch, side and line) gets a torch about every `TORCH_SPACING` (6) tiles from an unbiased random offset (`gen_range(0..TORCH_SPACING.min(len))`); runs under 3 cells get none; no two torches touch.
   - **Dark pockets:** each room and each corridor stretch (a connected piece of corridor floor between rooms, found by flood fill) is left without torches with probability `DARK_SHARE` (0.2).
   - **Never dark:** the start room and the boss hall are never dark, and always get at least one torch: if the normal rules give them none, a fallback puts one in the middle of their longest candidate run, whatever its length.
   - The result is `Dungeon.torches` → `Layout.torches` as `TorchSpawn { wall, side }`, and `Run::new` turns them into torch objects.

The test `guarantees_hold_over_many_seeds` checks 200 seeds (both themes), including chest placement (on floor against a wall, outside the start room and boss hall, not on an enemy), that chests and mimics actually appear, and the terrain guarantees: no safe tile cut off, spawns and chests on floor, no terrain in the start room, only chasms (and some) in the boss hall plus a lava pool in every lava-theme hall (none elsewhere), with its centre and entrance clear, only the theme's liquid, every terrain kind present, and a terrain share of 2–15 %.

## 7. Field of vision and light

`fov.rs` is recursive shadowcasting with the viewer's vision in tiles (9 for every hero today); walls (`Map::opaque`) block sight but are themselves visible. Terrain does not block sight. Sight alone shows nothing any more: **lighting replaced the fog**. Heroes have no light of their own, so a tile is only seen when it is in sight **and lit** (see "Light sources", §5). Unlit tiles are fully black. Sight and light are used in three places:
- **The hero's view (`vispoly.rs`, client `sim/view.ts`, the same rule, pinned by the shared fixture):** what a hero sees is its `View` (since 2026-10-16), computed from the viewed hero's **pixel position**. Open tiles count when any of 16 sample points (a 4×4 grid, 4 px apart) lies inside the visibility polygon (see "The vision mask" below); walls count when the tile FOV sees them. So, from the same position, the server sends monsters on the floor the client shows, with no black wedges where the two drift apart behind a corner. `View::compute` runs the FOV and the polygon (one per player per snapshot) and tests only the open tiles in the polygon's bounding box. The point-in-polygon test uses a binary search over the ray angles (the polygon is star-shaped around the viewer). `Player.view` replaced `Player.fov`.
- **Server snapshots (`visibility.rs`):** `seen(pos)` means on a tile of the viewer's view **and** (on a lit tile (static or moving layer, `Lights::lit`, the same rule as `is_lit`) **or** within `dark_reach`, the viewer's vision × darkvision, measured from the viewer). It uses the viewed hero's sight, so a spectator gets the teammate's view and darkvision; large figures count as seen if any of their corners is. Monsters, enemy projectiles, hazards, world objects and positional events are only sent when seen. Teammates are always sent, and so are the party's own projectiles, the `Dmg` of their hits and the `Boom` of their explosions (sent without a position), so a shot into the dark flies on and shows its hit instead of vanishing at the edge of the view. The lich drain beams keep their "boss fight on" rule.
  - **Torches** (world objects that own a light, `owns_light`) need sight only (`object_sent`): a torch in the viewer's FOV is sent even if it is out or its tile is dark, one outside the FOV is not. The client's light state does not depend on the torch entities (it comes from `RunStartInfo.lights` and the light events), and a torch sprite outside the FOV sits under full black anyway.
  - **Hero events (`on_hero`):** `Run::event_on_hero` marks an event (hurt and heal numbers on a hero) by its index in the tick's event list. Those are sent where the hero is in sight, lit or not; every other positional event needs sight and light. The client draws numbers on heroes (`Dmg.p`, `Heal.p`) over the darkness (`numberDepth`, `DEPTH.numbers`), so they show even when the hero is unlit.
  - **The moving-light list (`Snapshot.lights`):** every lit moving light within the viewer's FOV radius plus one tile plus its own reach (`lights_for`: a distance test with no line-of-sight check), as `MovingLight(x, y, kind, colour?)`. It can include glows from behind walls (§13). The monster that carries a glow is only sent when it stands in seen space.
- **Client light canvas (`LightField`, `LightView`):** replaces the fog canvas, see below.
- **Enemy perception:** `perception::sees` (above). **Behaviour change (2026-10-15):** humans (necromancer, summoner, lich disciples) do not see heroes in the dark; monsters (goblin and orc archers, orc warriors, mimic, ogre) only within a third of their vision (about 2.5 to 3 tiles); undead, demons and bosses see fully in the dark. A hero in light is seen as before. `simulation_is_unchanged_after_waking_the_boss` was re-recorded for this: in the lich hall the disciples stay idle in the dark and one orc loses the hero.

**The light canvas (`game/light.ts`, `game/lightview.ts`).**
- **`LightField`** holds the static lights (from `RunStartInfo.lights` and the light events; `GameScene.onEvent` calls `set`, `add`, `remove` and, on `Ev::Tile`, `mapChanged`) and builds the same static light map as the server with the `sim/fov.ts` port. The shared fixture (`export.rs` → `fixtures.json`, checked by `light.test.ts`) pins the TypeScript map to the Rust one, so a tile the server counts as lit is never drawn fully black, and no light is drawn on a tile the server counts as dark. Colours mix additively: each source adds `colour × intensity × falloff(distance / radius)` per tile and channel, capped at 255 (torch plus lava gives orange, blue plus red purple). The falloff is a smoothstep from 1 at the centre down to `EDGE` (0.1) at the radius edge, never brighter further out, so a light fades out **inside** the tiles it lights. Moving lights from the snapshot are added each frame with the same falloff (`addMoving`): a radius-r shadowcast from the tile of the sent position (`Math.floor(px / TILE)`, the server's `light_tile`), the same tiles the server's moving layer marks; the shared fixture also pins these (moving lights in the open, beside a corner, against a wall and exactly on a tile corner).
- **Two canvas textures** (`LightView`), 280×280, **2 px per tile** (`SUB`), scaled ×8 and drawn with LINEAR filtering. The values are worked out per tile, then upsampled with Catmull-Rom (`upsample`, separable, 4 taps per axis; the image data clamps its overshoot): one pixel per tile with LINEAR filtering is plain bilinear, which showed creases along the tile grid in the long fade (screenshots, 2026-10-15). Afterwards `blackenDarkTiles` sets every SUB×SUB block of a dark tile (darkness 255: out of sight or unlit) back to full darkness and no tint, so the fade stays on the lit side of the boundary: with the cubic taps alone, the centre of a dark tile next to a bright one got 10 to 13 % light, more than the dimmest lit rim, and read as lit floor where no monster is sent. It costs about 0.5 ms per frame for the whole window (measured in Node, 66×40 tiles):
  - the **darkness** (`DEPTH.fog` 7000): alpha 1 on every tile not in the viewer's FOV or not lit; on lit tiles in the FOV the alpha is `1 − max(brightness, MIN_LIT)`. `MIN_LIT` (0.08, about the falloff's edge) keeps a lit tile from ever being fully black while its rim really fades;
  - the **tint** (`DEPTH.tint`, MULTIPLY blend, just below the darkness; the warm light, #148): each tile's summed light colour becomes a multiplier (`warmTint` in `lightview.ts`): per channel `255 * (1 - s * (1 - c / max))` with `s = WARM (0.45) * min(1, max / 255)`, `c` the channel of the summed colour and `max` its brightest channel. Near a torch, stone and figures keep their own colours and turn warmer, never paler (the old additive tint washed them out). Tiles that are not seen and lit get white (no change); `blackenDarkTiles` still writes alpha 0 there. `LightView.light(x, y)` and `LightView.seenLit(x, y)` give the per-tile brightness and colour and the seen-and-lit test to `Mood`.
- **The vision mask (`game/visionmask.ts`, `sim/vispoly.ts`):** the edge of sight is drawn as straight shadow lines, not along the tile grid (the user's request, 2026-10-16).
  - `visibilityPolygon` (pure, `vispoly.test.ts`) builds the area seen from the viewer's **pixel** position. Wall edges that face open tiles are merged into segments, and rays go to every segment end (± 1e-4 rad, so a ray grazing a corner continues behind it) and at 96 even angles. Each ray stops at the nearest segment or at the sight radius `sightRadius(vision)` = `(vision + 0.5) × TILE` px, so the outer edge is a circle covering the tiles the shadowcast reaches. It costs about 0.05 ms per polygon (measured in Node on the fixture map, vision 9).
  - `LightView` keeps the viewer's `View` (`LightView.view`, the hero's view above). It recomputes it when the viewer moves (to 0.1 px), the rounded vision changes or the map changes (`mapChanged`, on `Ev::Tile`). Darkness, tint and darkvision use `seenForLight`: the view plus open tiles next to an open tile in view, so a tile the polygon only grazes (no sample point inside) stays lit and the darkness does not fade the edge into tile-shaped notches; the extra tiles lie under the mask apart from slivers under 2 px. The mask's edge therefore cuts through lit floor. Walls outside the FOV stay black. (`wide` off, E in `?lights`: the tile FOV only, the old edges.)
  - `VisionMask` draws the view's polygon in white into a canvas over the camera window (plus 2 tiles a side) at **8 px per tile**, plus every visible wall tile whole (the polygon stops at a wall's face, so it would cut off brick faces and rims). A Phaser `Shader` game object at `DEPTH.fog + 0.5` draws black with alpha `1 − mask`. The edge is crisp (only the canvas's antialiasing): a blurred fade was tried and made the shadow behind a pillar look too wide. A game object and not a camera post effect, so the drain beams and the numbers above the darkness stay visible. The canvas is redrawn and uploaded when the window origin or the view's `version` changes, so while the hero walks that is nearly every frame (a canvas of about 360×224 px; not measured live). The window only grows.
  - Out of sight is pure black. A dim map memory and a fog look were demoed and rejected (2026-10-16).
- **Filtering:** Phaser resets a canvas texture to NEAREST filtering on every `refresh()` under `pixelArt`, so `LightView` sets LINEAR again after every upload.
- **Flicker:** each light's brightness wobbles by its kind's `flicker` and a per-light phase (`flicker(kind, id, t)`, two sine waves).
- **Redraws:** `LightView.update` runs every frame, but redraws only the camera's tile window plus 3 tiles (`MARGIN`: the upsampling reads two tiles around each one; about 66×40 tiles), so flicker and moving lights cost little. A torch's radius 7 means up to 225 tiles per torch, from a cached shadowcast. The viewer's FOV is recomputed when the viewer's tile changes or the map does.
- **Sound text (the rule, 2026-10-16):** text that stands for a sound is drawn **above** the darkness at `DEPTH.sound` (7500), so it shows even where nothing else does: the wolf's "grrrr" and the sleeper's "Z". It uses `SOUND_TEXT` (`game/effects.ts`): a dark fill `#1a1020` with a light outline `#d8d0e0` (a pale fill vanished inside the pale outline), set per call as `fx.text(..., SOUND_TEXT.fill, false, DEPTH.sound, SOUND_TEXT.stroke)`. Damage and heal numbers are not sounds and keep their rule below. A sound only shows for an entity the client has: heroes and the wolf are always sent, an enemy in the dark is not (no enemy sound exists yet).
- **Draw order:** every figure and shot is drawn **under** the darkness, heroes, teammates, their name tags (children of the figure's container) and the party's shots (also the own predicted ones) included, so a hero on an unlit tile vanishes like a monster (the user's decision, 2026-10-15). Glowing shots still show because they carry their own light. Numbers (damage, heal, immune) and HP bars on heroes and allies are above the darkness (`DEPTH.heroBars` 7999, `DEPTH.numbers` 8000), so they show even when the hero is unlit. Monster numbers and HP bars are under it (`DEPTH.enemyNumbers` 6501, `DEPTH.enemyBars` 6500), chosen by `numberDepth(p)` (from `Dmg.p` or `Heal.p`) (the user's decision, 2026-10-23). Above the darkness: the vision mask (`DEPTH.fog + 0.5`), then the HUD, the E hint, the lich drain beams and the debug paths.
- The renderer knows nothing about torches, lava or projectiles: it draws whatever the registry sends. Lava keeps its pulsing glow sprites (`terrain.ts`), which sit under the darkness and only show where lit.

## 8. Netcode and responsiveness

**Input (`GameScene.fixedStep`).**
- Inputs are sent at a fixed 60 Hz. Each step carries movement, the aim, and a shot id when an ability fires; the client fires when the button is held or was clicked and its local cooldown is ready.
- WebSocket `TCP_NODELAY` is enabled on the server listener.
- **Cache headers** (`cache_headers` in `main.rs`): hashed Vite bundles (`/assets/index-*`) are `immutable`; everything else (`index.html`, the atlas) is `no-cache`. Without this, a browser could keep running an old client against a new server, and the tile rules and prediction would disagree.

**Prediction (`world.ts` `Predictor`).**
- Local movement uses the TS collision port. It is bit-identical to Rust, which `sim.test.ts` checks against the Rust-written fixtures.
- On each snapshot the client replays unacknowledged inputs from the server state.
- Errors under 24 px are blended out over about 100 ms; larger errors snap.
- Terrain is part of the port: the speed factor and the walking rules.
- **Solid objects are part of the port** (`Predictor.solids`): the squares of resting barrels from the latest snapshot go to `stepMove`, like the server's `Run::solids`. A barrel moves only after a push or sinks, so prediction next to barrels should need no correction; that is part of the open live check.
- **Knockback is part of the port** (`stepMove`, `knocked()`). `me` carries `knock_vx/knock_vy`, and the replay starts from them, so after the snapshot that reports a push the prediction slides exactly like the server. The push itself is the enemy's action, so the client learns of it about RTT/2 late (a correction, blended or snapped as usual). While predicted knocked, `fixedStep` fires nothing, and the replay drops dashes sent during a push the client learned of late, like the server. The predictor also applies the server's sinking rule (`sinking()` in `sim/collision.ts`): a hero not dashing whose centre is over a chasm or deep water stops moving and attacking, in prediction and in the replay, so a fall needs no round trip and causes no correction. The pending list keeps each input as it was sent, not as predicted: if the server sees no fall (or a debug climb-out already happened there), it applies the move, and the replay must too.
- Local cooldowns are corrected when they differ from the server by more than 0.15 s. The server value is first carried through the inputs it has not acknowledged yet, including the abilities they use (`Pending.used` for cooldowns; like the movement replay). Without that, a snapshot from before the server saw a shot showed cooldown 0, the client reset its own, and a held button fired a second, client-only shot (seen as two arrows when dragging the mouse while clicking).

**Own attacks.**
- `predictAbility` starts the animation, cooldown or dash locally (the ranger's `SummonWolf` only the cooldown: the wolf itself is not predicted) and spawns cosmetic projectiles.
- The matching server projectile (same `shot_id`) is hidden, also for 2 s after the cosmetic one has ended (`endedShots`). The cosmetic one ends when the server one disappears, at a wall, or at the first enemy it touches (`sim/hitbox.ts`, the port of `Monster::shot_dist` with the exported `HITBOX` table; sampled every 4 px; `ResolvedAbility.projectile` is an `EntityKind`, sent as its id). Without the enemy check a shot that hit within the first ticks never appeared in a snapshot, and its cosmetic copy flew on through every enemy behind.

**Remote entities (`Interpolator`).**
- Snapshots are placed on a server-tick timeline using an estimated clock offset (a low envelope of arrival offsets).
- Remote entities are rendered behind that timeline by an adaptive delay of 1.5 snapshot intervals + 2.5× jitter, clamped to 50–300 ms.
- Brief extrapolation of at most 100 ms covers a missing snapshot.

**Measuring.**
- F3 overlay: FPS, frame time, ping, jitter, interpolation delay, snapshot bytes, prediction correction, server ms per tick, darkvision.
- F4 (debug runs only): cycles your own hero's darkvision 0 -> 50% -> 100% -> 0 via `DebugDarkvision` (the server honours it only in a debug run). The client ignores F4 unless the run is a debug run and your hero is alive. While darkvision > 0 the main camera carries the `DarkvisionFX` post pipeline (`client/src/game/darkvisionfx.ts`), which greys the scene where LightView's `dvmask` is set; it is removed at 0. In darkvision reach a tile is never darker than `DV_DARK` (0.45), lit or not, and the mask fades out as a light gets brighter than darkvision (`dvMask`): without this, the dim rim of every light was darker than the darkvision around it.
- F9 (debug runs only, alive): toggles immortality via `DebugImmortal` (the server echoes it in `DebugPath.immortal`; the badge shows MORTAL).
- F8 (debug runs only, alive): cycles `DebugEffect` through every `EffectKind` (blind, sleep, petrified, slowed, accelerated, burning, frozen, poisoned) on your own hero, with the default duration; the server shows "name: Kind" as a message. Use it to see the HUD icons, the lying pose and the stone look without a lich.
- `?lag=&jitter=&loss=` simulates conditions in both directions, keeping TCP ordering (`DelayLine`: one FIFO queue and one timer, because browsers round timer delays down to whole milliseconds; a timer per message delivered inputs out of order, which the server then applied out of order, and that caused most of the corrections once seen in busy runs under lag).
- In a busy debug run under `?lag=150&jitter=40&loss=2` (bot walking to the demon and fighting it for 90 s), about 36 of 2,760 snapshots still correct the prediction: almost all are pushes, which the client learns of about RTT/2 late, plus the force field closing during a dash.

**Typical numbers (local):**
- server tick about 0.12–0.14 ms
- snapshot about 127 B with 2 players (the knock is `[vx, vy]` only while pushed, nil otherwise) (248 B before the compact form); a fight with 14 entities in view about 350 B (about 570 B before). Each extra entity costs about 19 B.
- correction 0.00 px

**The dungeon air (`game/mood.ts`, #148; the user approved the look on 2026-10-24).** `Mood` is created after the `LightView` in `GameScene.create`, updated each frame right after `lightView.update` (same `dt` in seconds as `Effects.update`) with the lit and unlit torch entities (`x`, `y`, `extra` side, `anim === 1` lit) and the snapshot's moving lights, told of terrain changes in `mapChanged` (the `Tile` event; it collects the lava and water tiles again) and destroyed in `cleanup`. - **Layers and depths** (`DEPTH` in `effects.ts`): the air draws over figures, shots, spells and effects and under enemy HP bars and damage numbers, the tint and the darkness: `airHaze` 6490 (a thin cloudy layer over the whole map: two tiling sprites of a generated 128 px cloud texture, tint `0x8a7c6c`, alpha 0.10 and 0.07, drifting), `airDust` 6491 (faint motes in loose clouds, shown only on a seen and lit tile, brighter where the light is, coloured by the light's hue blended halfway to white, ADD), `airSmoke` 6492 (lava smoke), `airDrips` 6493 (a drop falls into a water tile and leaves two flattened ripple rings and a splash), `airEmbers` 6494 (orange sparks over lava, a trail behind Fire moving lights, one burst when a Blast light first shows). **Canvas and zoom (UI polish).**
- The Phaser canvas renders at **screen resolution**: `viewSize()` in `main.ts` picks an integer zoom (the window divided by 600 x 340, rounded, at least 1) and the view in world pixels (window / zoom); the canvas is view x zoom, and Phaser's own scale zoom is 1. The zoom sits on each scene's main camera (`cam.setZoom`), applied by `applyView` on the scene's `CREATE` event (before its first frame) and again on a resize. Every scene but the game has origin (0, 0) so the world's top left stays the screen's top left; `GameScene` keeps the centred camera. `LightsDemoScene` fits its own zoom.
- Why: text in the world is Inter and needs real pixels. The old canvas was the view in world pixels (640 x 360 at 1280 x 720) scaled up by CSS, which turned 6.5 px text into a smear. World sizes are still in world pixels; the sprites stay crisp because the game keeps `pixelArt` (NEAREST).
- Cost: the canvas has zoom squared times more pixels (4x at 1280 x 720). The smoke test's frame rate in headless swiftshader fell from about 27 to about 15. Not measured on a real GPU (TODO).

**World texts (`game/worldText.ts`, `game/keycap.ts`, `Effects.text`).**
- All text drawn in the world uses Inter (`FONT_TEXT`). `WORLD_TEXT` holds the sizes and styles in world pixels (tag 6.5 px at 600, number 7 px at 800, crit 9 px at 800 in gold `#ffd24a`, mark 7 px for the sleep Z and the "!", sound 6 px italic, small 6 px for "+N coins" and "IMMUNE"); at zoom 2 that is about 13 screen pixels for a name tag. `TEXT_RESOLUTION` (4) is the text texture resolution.
- `smoothText(t)` sets LINEAR filtering on a Text's texture and again after every `updateText`, because `pixelArt` makes text NEAREST, which aliases when a 4x texture is drawn smaller.
- `Effects.text(x, y, s, color, opts)` takes `{ big, depth, stroke, kind }` (`kind` is a `WORLD_TEXT` key). A crit is its number alone in gold at the crit size, with a short pop (`popScale`: 1.4 easing to 1 in 0.12 s); the old "CRIT" word is gone.
- `KeyCap` (`game/keycap.ts`) is the use hint: a gold key cap with a dark "E" and an optional white label ("Wake") to its right. `set(label | null)` shows it (null: the bare cap, at a chest or door), `hide()` hides it.
- Two text resolution policies exist: world texts use the fixed `TEXT_RESOLUTION`, the rules-log tags use zoom x camera zoom x devicePixelRatio (TODO).

**Fonts.** Self-hosted, no CDN: `client/public/fonts/` holds Inter (variable, weights 100 to 900, normal and italic, latin subset) and IM Fell English SC (400, headings only), both from the Fontsource npm packages (5.3.0) with their OFL licence texts. `client/src/fonts.css` has the `@font-face` rules and is imported by `style.css` and `admin/admin.css`. Sizes: body 15 px, small 13 px, smallest 11.5 px, HUD 13 px, nothing in the HTML UI below 11 px; digits that change in place use `font-variant-numeric: tabular-nums`.

## 11. Extending

- **New class:**
  - server: add a `ClassId` variant (`protocol.rs`), a `classes.rs` entry and an `EntityKind`; reuse or add `AbilityId`s with an executor in `run/abilities.rs`
  - client: add to the `FIGURES` entry, `ui/text.ts`, and `FIG`/`CLASSES` in `ui/classes.ts`
  - database: add a migration that widens the `characters.class` CHECK constraint
  - then run `cargo test`
- **New ability:** see "How to add an ability" in §11a.
- **New enemy:** add an `EnemyType` + `def()`, its `EntityKind`, population in `generate.rs::populate`, and a `FIGURES` entry. (The mimic is the exception: it is placed by `place_chests` and drawn by its own `MimicView`, not a `FIGURES` entry.)
- **New boss:**
  - server: add a `BossId` variant, a `defs/bosses.rs` entry and a new `run/bosses/<name>.rs` implementing `BossBehaviour`, plus a `create()` arm
  - client: add the `EntityKind` and a `FIGURES` entry, `BOSS_TEXT` in `ui/text.ts`, and `BOSSES`/`BOSS_FIG` in `ui/lobby.ts`

**How to add a light source** (see "Light sources" in §5). No client change is needed: the client draws whatever the registry sends.
1. **A new kind:** a row in `LightKind` and `def()` in `defs/lights.rs` (radius in tiles, default colour, intensity, flicker). Add it to `LightKind::ALL`. `cargo test` regenerates `LIGHT` in `defs.ts`.
2. **A static source** (fixed on the map: a brazier, mushrooms, goo, a fountain): `run.add_light(kind, Anchor::Tile(x, y), colour)` while the run is built (it goes out in `RunStartInfo.lights`) or later (it sends `Ev::LightAdd`). If it can be switched, keep its id and call `set_light(id, on)`; `remove_light(id)` deletes it. Torches are the example: a world object that owns the id (`ObjState::Torch.light`) and calls `set_light` from `set_torch`. A source on a tile that changes through `Run::set_tile` should be added and removed there, as lava is.
3. **A moving source** (a glowing enemy, a hero spell or item, the carriage lantern): either list the entity kind in `kind_light`, which attaches the light at spawn for every projectile and hazard, or call `add_light(kind, Anchor::Entity(id), colour)` explicitly (e.g. `Anchor::Entity(hero_id)` for an own hero light). The sweep removes it when the entity is gone.
   - **A flash** (an explosion, a spell burst): `run.add_flash(kind, pos, secs)`, a light on a spot that the sweep removes after `secs`. `Blast` (explosions) and `Holy` (the healing wave) are the examples.
4. **Colour override:** the `colour` argument of `add_light` (`None` = the kind's colour), or `set_light_colour(id, colour)` at any time (a cursed torch turning blue); a static light sends `Ev::Light` with the new colour, a moving one changes its `MovingLight` entry.
5. **Asking:** `run.is_lit(pos)` for game rules (the shadow, the torch-extinguishing enemy; those also use `set_light`).

**How to give a creature darkvision or longer sight** (see "Sight" in §5). No client change is needed.
1. **A whole kind:** change the race's `Sight` in `race_def` (`defs/races.rs`): `vision` in tiles, `darkvision` as a share of vision (1.0 = it sees an unlit target as far as a lit one).
2. **One enemy or hero class:** set `vision` and/or `darkvision` in its `Adjust` (`defs/enemies.rs`, `defs/classes.rs`); the profile takes it. An enemy's `vision` is in tiles.
3. **A boss:** `defs/bosses.rs` (25 tiles today); `bosses::target` already uses the same rule.
4. Add or adjust a test for the new numbers (`perception.rs` has the pattern: a dark map, a target at several distances). The hero filter and the greyscale follow `Player.sight` and the `SelfW` value by themselves.

**How to add an effect** (see "Status effects" in §5).
1. **The kind** (`defs/effects.rs`): a variant of `EffectKind` with the next id (the id is a bit of a `u16`, so 16 kinds at most and one is left after plan 3b; a compile-time assert checks it). `listed_enum!` adds it to `ALL` and `COUNT`.
2. **Its numbers:** an arm in `def`: duration, `positive`, `mods` (a `const` slice of `StatMod`s), the flags and, for damage over time, `dot`, `cancels` and `ends_in_water`; `save` if it is not saved with CON or WIL, `flees` for a Fear-like rule, `replaces` and `resisted_by` for a tier. A damage-type effect is one line in `TYPE_EFFECTS` (`defs/effects.rs`, with the least share) plus its `resisted_by` (tests check they agree): every hit with that type as at least that share of its split then applies it (the highest tier it meets), with no source code of its own. The resolution order and the resistance cap are in §5. Nothing else on the server changes: speed, vision, resistances, knockback and the flags already read the resolved values.
3. **A source:** a spell or an enemy, either `Damage::with_effect(OnHit { kind, secs, magical, power, look })` on its hit (`magical` picks the WIL save unless the effect names its own `save`, `power` is the source's key Attribute, `look` how it is drawn), or `run.apply(Creature::..., Apply { kind, secs, power, magical, look, source })` for something that is not a hit (`apply_effect_from` is the short form; an `OwnEffect` on an ability does this for an area ability). A source that frightens needs `source: Some((id, pos))`. There is no chance: an effect always applies. Use `apply_effect` (unscaled) only in debug code and tests. For a monster's or a hero ability's hit effect, fill `defs/enemies.rs::on_hit` or `defs/abilities.rs::on_hit`. The lich (`run/bosses/lich.rs`) is the example.
4. **Its resistance exists already:** `EffectResistances` has a slot per kind, 0 on every creature. Give a race or a boss some in its `RaceDef` or `Adjust` (`effect_res`). A damage-type effect gets none: its type's damage resistance resists it.
5. **Client:** run `cargo test` (it regenerates `EFFECT` and `EFFECTS` in `defs.ts`), then add the visual: `StatusView` in `game/status.ts` for marks around the figure, `EntityView` for a tint or pose; a new `EffectLook` is one more column in the look tables there (they are `Record<Look, ...>`, so a missing one fails to compile). Add its symbol to `EFFECT_ICON` (`ui/effectIcons.ts`; the `Record` is typed by effect id, so `tsc` fails until it is there, and `effectIcons.test.ts` checks the symbols are distinct) and a row to the gallery (`GalleryScene`).
6. **Tests:** a `resolve_stat` case in `defs/effects.rs` and one for the source; if a flag gets a new meaning, one where it is enforced.

**How to add a damage type** (for example holy):

1. **The variant:** a line in `DamageType` (`defs/damage.rs`) with the next id, and its `name()`. `listed_enum!` puts it in `ALL` and `COUNT` and refuses a gap in the ids at compile time, so every per-type array (resistances, splits) grows with it: every creature resists it at 0 until a race or `Adjust` says otherwise.
2. **Client:** run `cargo test` (it regenerates `DMG_TYPE`), then give it a colour in `DMG_COLORS` (`game/damage.ts`; its test fails until you do).
3. **Optional:** a damage-type effect for it is a row in `TYPE_EFFECTS` plus an effect with that `dot` ("How to add an effect"). `EffectKind` uses `listed_enum!` too, and asserts it fits the `u16` snapshot mask.

**How to add a level type** (see "Levels" in §5; the dungeon is the example):
1. **Protocol** (`protocol.rs`): a `LevelId` variant and a `LevelChoice` variant with the level's options (e.g. `Escort {}`; the tag is `level`). Run `cargo test` to regenerate the TS types.
2. **The level** (`run/levels/<name>.rs`): a struct with the level's state, a `build(seed, …options, rng) -> (Layout, Self)` that makes its map (its own generator) and fills the shared `Layout` (map, enemy spawns, chests, player spawns; empty lists are fine), and `impl LevelRules` overriding only the hooks it needs: e.g. `populate` for its own monsters or objects, `tick` for a moving goal, `on_killed` or `post_tick` to set `run.ended = Some((true, run.time + END_DELAY))` on a win, `failed` for its own way to lose, `debug_target` for the debug path.
3. **`Level`** (`run/levels/mod.rs`): a variant holding the struct, and one arm in `build` (from its `LevelChoice`), `id`, `boss`, `boss_mut` and the `dispatch!` macro. `pub mod <name>;` next to the others.
4. **A boss, if it has one:** a `BossEncounter` field (`BossEncounter::new(boss_id, arena, door)`), returned by `boss`/`boss_mut`, and the `boss::` functions as the hook bodies, as `DungeonLevel` does. Without one, `boss()` is `None`: no boss bar, `RunEnded.boss` is `null` and the statistics show the level alone. Note: `BossEncounter::check_arena` currently wakes every sleeping non-mimic monster on the whole map. That is dungeon behaviour, so a second level that includes a `BossEncounter` should move the map-wide wake into `DungeonLevel::post_tick` or make it a parameter.
4a. **State of its own, if it has any:** hooks are associated fns over `&mut Run` with no `&self`, so a stateful level reads its state through a small accessor that matches `run.level`, plus a `_mut` variant, e.g. `fn state(run: &Run) -> &EscortLevel { match &run.level { Level::Escort(e) => e, _ => unreachable!() } }`.
5. **Client:** a `LEVEL_TEXT` entry in `ui/text.ts` (name, victory and defeat line of the end screen). The map arrives as tiles like the dungeon's; new tile kinds need their own art and rules.
6. **Lobby** (`lobby.rs`): map the room's choice to the new `LevelChoice` in `start`. Today every room is `LevelId::Dungeon`; offering a second level needs a level picker and a `SelectLevel` message (not built yet).

The database, statistics, telemetry and the admin page take the level as text (`format!("{:?}")`), so they need no change.

## 11a. Accounts, characters and progression

**Accounts (`auth.rs`, `api.rs`).**
- An account is a name and an Argon2id hash (19 MiB, 2 passes, 1 lane, run in `spawn_blocking`). No e-mail and no other personal data are stored, so a lost password cannot be recovered.
- Names are 3–16 of `A-Z a-z 0-9 _ -` and unique ignoring case, for accounts and characters alike. Passwords are 8–128 characters.
- A login for an unknown name still checks a dummy hash, so the timing does not reveal which names exist.
- **Throttling** (in-memory `Limiter`):
  - 5 failed logins per account name in 30 s, and 20 per IP in 5 min, give a 429.
  - At most 10 registrations per IP per hour.
  - Deleting an account rechecks the password through the same limiter.

**Sessions.**
- Login creates a random 32-byte session id. The browser gets the cookie `ta_session` (HttpOnly, SameSite=Strict, Path=/, plus `Secure` if `COOKIE_SECURE`) holding `base64url(id ‖ expiry) . base64url(HMAC-SHA256(SESSION_SECRET, id ‖ expiry))`.
- The table `sessions` stores only `sha256(id)`.
- **Idle timeout:** a session ends after `PLAYER_SESSION_MINUTES` without activity (default 10080 = 7 days). `sessions.expires_at` is the end unless the player is active again, and activity moves it forward:
  - every API request with the session, the WebSocket connect included (`db::touch_session`, one `UPDATE … RETURNING`);
  - the end of a game connection (`db::extend_session`), because a player who was connected was active all along, even through a run longer than the idle time. A session deleted meanwhile (logout, new password) stays deleted.
- **Hard limit:** the token's own expiry and the cookie's Max-Age are 1 year (`SESSION_MAX_SECS`). Even an always-active player logs in again after a year.
- **Checks on every request** (the `Session` extractor):
  1. signature (constant-time) and expiry, without the database, so forged tokens cost nothing;
  2. the session row (alive, and then extended), so logout, account deletion and idling end it.
- JavaScript never sees the token.
- CSRF is covered by SameSite=Strict, JSON-only state changes and the WebSocket origin check.

**One connection per account.**
- `Lobby::connect` closes an older connection of the same account (Error "You logged in from another window." + close).
- A character therefore plays in one place only, and XP cannot be banked twice.
- A closed connection's late messages are ignored (`handle` checks that the connection still exists).

**Characters.**
- Rows in `characters` have a name, a class that never changes, and `progress`. There are at most `db::MAX_CHARACTERS` (8) per account; the account row is locked while counting.
- The lobby keeps a cached copy (`Conn.character`) of the selected one.
- **Progress document (`progress.rs`):** `characters.progress` is JSONB: `Progress{version, rev, xp, total_xp, coins, bought, nodes, xp_spent, equipment, inventory, loadout}` (version 2; §11a "Attribute shop, skill trees and keystones").
  - Every field is `serde(default)` and unknown fields are ignored.
  - Reading goes through `Progress::from_json`, which runs `upgrade()` (version steps) and starts fresh if a document is unreadable (logged).
  - *To change progression:* add fields to the struct; no SQL migration is needed. Only if old data must be converted, bump `CURRENT_VERSION` and add a step to `upgrade()`. Old rows are converted on read and written back on their next save.
- **Writes** all go through `db::modify`: `SELECT … FOR UPDATE`, change the struct in Rust (`Progress::bank`, `Progress::apply`), `UPDATE`.
  - The row lock serialises concurrent changes, so a purchase cannot race with banking.
  - Every save bumps `rev`; `Lobby::apply_progress` ignores results older than its cached copy.
- **Earning:** `kill_monster` adds `xp_for_kill` and `coins_for_kill` (mimic 25, boss 50) to each living player; chests add `CHEST_COINS`.
- **Banking:** when the run task ends (victory, defeat or everyone left) it calls `lobby::finish_run(rid, run.awards(), run.record(outcome))`.
  1. The room closes and the players return to the lobby.
  2. Then `db::bank_awards` banks every `Award{character, xp, coins}` in one transaction, in id order (account rows first, `FOR SHARE`).
  3. Then `apply_progress` sends `Character` to the players.
  4. Last, `db::record_run` stores the run for the statistics (§11b). A failure there is only logged.

  Debug runs bank like normal ones; `bank_awards(…, debug_run)` skips a character whose account's flag differs from the run's kind (see "Debug accounts").
- **Spending and build changes:** the five build messages and `DebugGrantItem` are handled in `main.rs` by `change_build`: `Lobby::can_change` (Ruling 8: not during a run, not while Ready), then `db::update_progress(…, |p| p.apply(class, change))` (a `progress::Change`), then `apply_progress`. The lobby lock is never held during a query.
- **Coins** pay for a respec (below); nothing else costs coins yet.
- **Applying:** `Lobby::build_of` takes the character's saved build (`Progress::build`, with the debug picks on top) into `Member.build`. `Run::new` turns them into `Player.sheet`, which the simulation uses; `RunStartInfo.speed`, `abilities` and `fallback` send the resolved numbers to the predictor.
- **Tuning:** `defs/progression.rs` holds only the XP and coin rewards; prices are `attr_price`/`ATTR_WEIGHT` (`defs/attributes.rs`), node costs and bonuses `defs/trees.rs`, `RESPEC_*` in `progress.rs`, keystone numbers `sheet.rs` and `run/keystones.rs`.

**Debug accounts (#151; spec [2026-10-24-debug-accounts-design.md](superpowers/specs/2026-10-24-debug-accounts-design.md)).** Debug mode is a developer tool: only accounts the admin marks (`accounts.debug`, migration 0006) can use it, and debug never reaches a normal game.
- **The database is the authority for everything saved.** `Change::is_debug` (free buys, free respec, grants) is decided by the change itself; `db::update_progress` saves such a change only if the account's flag is set at that moment, read in the same transaction (`FOR SHARE` on the account row, the character row locked). `db::bank_awards(awards, debug_run)` banks a character only if its account's flag equals the run's kind (a mismatch is logged and the award dropped), which covers a player kicked by an unmark whose debug run ends later.
- **Lock order:** the account row first, then character rows by id (as `create_character` and account deletion do). `set_account_debug` locks the account `FOR UPDATE`, flips the flag and, on unmark, writes `Progress::new(class)` to every character (keeping and bumping `rev`), in one transaction; the caller closes the account's connections after the commit (`kick_account`). Marking keeps the progress.
- **In memory:** `Conn.debug` is read from the database at WebSocket connect and sent in `Welcome`. A room's kind is fixed by its creator; `JoinRun` refuses the other kind; the lobby lists each connection only rooms of its own kind; "Mixed party." guards the start; a character whose account kind differs from the connection's is refused. Debug messages are refused unless the connection (lobby messages) or the run (in-run messages) is debug. `Run.debug` comes from the room and is stored as `runs.debug`.
- **Migration 0006 wipes** every existing character's progress once (`UPDATE characters SET progress = '{}'`), because debug changes made under the old `?debug` cannot be told apart. It also resets `rev` to 0 (harmless: it runs at server start, before any session).
- **No `ALLOW_DEBUG`**, no `?debug` and no URL boss preselect any more. No marked account means debug is off for everyone; with the admin area disabled nobody can be marked through the admin page.

**The character sheet and Attributes (progression plan 1; spec [2026-10-18-progression-design.md](superpowers/specs/2026-10-18-progression-design.md)).** The shop and the tree are in "Attribute shop, skill trees and keystones" below.
- **Where the numbers come from.** `sheet.rs` resolves every hero and monster number from a class or stat block plus its Attributes. `hero_sheet(class, &Build)` gives a hero's `Sheet`: max HP, speed, weight, resistances, effect resistances, melee split, sight, the two abilities (`ResolvedAbility`) and the Ranger's melee `fallback`. `enemy_stats`, `boss_stats` and `wolf_stats` do the same for monsters. The run reads `Player.sheet` and the monsters' stats; it no longer reads `defs` numbers for these directly.
- **Attributes** (`defs/attributes.rs`): STR, DEX, CON, INT, WIL, CHA, as `Attributes`. A hero's Attributes are the class's points plus the race bonus (`classes::start_attrs`) plus `extra` (shop and item points; see "Attribute shop, skill trees and keystones"). Per point from 10:
  - STR: melee damage 5 %, ranged range and projectile speed 2 %.
  - DEX: finesse and ranged damage 5 %, arc 3 %, attack and firing speed 2 %.
  - CON: 5 max HP and 1 % move speed.
  - INT: spell damage 5 %. CHA: innate damage and heals 5 %.
  - WIL: the save against magical effects.
  - The rule is `factor(v, pct) = max(0.1, 1 + pct × (v − 10))`, and `hp(base, con) = base + 5 × (con − 10)`.
- **The `Scaled` rule is bit-exact.** A scaled number is stored as its value at a reference Attribute value, `Scaled { value, attr, pct, at }`, and resolved as `value × factor(cur, pct) / factor(at, pct)`. At the start Attributes the ratio is exactly 1.0, so today's numbers (and the fingerprint tests) come out unchanged to the bit. Do not write it as `base = today / start factor`: floats would drift. Cooldowns use `per`, which divides.
- **Races** (`defs/races.rs`, formerly entity types): Human, Elf, Magical Beast, Goblin, Orc, Ogre and so on. A race carries damage and effect resistances, sight and an Attribute bonus. Only the Elf has one: DEX +2, so the Elven Ranger is class 10/13/12/8/14/13 plus 2 DEX = 10/15/12/8/14/13. The Dire Wolf's race Magical Beast adds +20 % cold resistance as its `Adjust`.
- **Weights and pushes.** Every creature and object has a weight (Wizard 9, Paladin 12, Barbarian 13, Ranger 10, bosses 40, barrel 6, chests 40, Dire Wolf 10). A push moves a target `base × min(1, (STR − weight) / 4)` px, and not at all unless the pusher's STR is above the weight (`attributes::push_dist`). Bosses push with `BOSS_KNOCK_STR` (30) and barrel blasts with `BARREL_BLAST_STR` (18).
- **Effect durations** (`apply_effect_from`, `scaled_secs`): a harmful effect lasts `base × max(0, 1 + (power − save) / 20)`. The save is the target's WIL for a magical source and CON for a non-magical one. Damage-type effects (`type_effect_hit`) are non-magical and use `max(TYPE_EFFECT_POWER, Damage::power)`: the hit carries its source's governing Attribute (spec §5, the user's ruling of 2026-10-19). It is set where the hit is built: hero abilities by `abilities::governing` (spells INT, Heal CHA) from `sheet.attrs`, and weapon abilities (those with `ab::uses_weapon`; `governing` returns None for them) by the weapon's `ResolvedWeapon::power`, the wielder's key Attribute, chosen in `hero_power` in `run/abilities.rs`; monster shots in `spawn_monster_projectile` from the owner's `attrs` (`enemies::governing`: imps' and chorts' fire bolts CHA, the summoner's INT, arrows DEX; `bosses::governing`: the demon's and dragon's fire CHA, the lich's spells INT); enemy melee and the wolf STR; the dragon's breath CHA. Explosions keep their shot's power. Lava, barrels, burning ground (`FirePatch`), effect ticks and shots whose owner is unknown carry 0, so 10. Positive effects are never scaled. The creature's effect resistance applies after (`effect_secs`). An effect that names its own `save` uses it (Entangled STR, Fear WIL). **Entangle's pulses:** each 1 s Entangled pulse of the roots is scaled by the STR save separately, so a weak target stays rooted somewhat longer than 1 s after the roots end (about 1.6 to 2 s for a goblin at CHA 14 and up); the spec's "at most 1 s" predates the user's choice of STR as the save.
- **`RunStartInfo`** carries the receiving hero's resolved `speed`, `abilities` (primary and secondary) and `fallback` instead of the old `mods`. The client predicts movement and cooldowns from these numbers as sent. It never computes an Attribute formula, so the server's rule has one home.
- **Export:** `export.rs` writes `CLASSES` with `attrs` (start totals, class plus race), `weight` and `base_hp`; they are for display and the demo scenes.

**Weapons, items and equipment (progression plan 2).**
- **Weapons** (`defs/weapons.rs`): `WeaponKind` (19 kinds, spec §6.1) has a `WeaponCategory` (Melee, Finesse, Ranged, Thrown, Natural) from `category()`. `key_attr(category)` gives the Attribute that governs its damage and the power of its effects: STR for Melee, Thrown and Natural, DEX for Finesse and Ranged. Both are exhaustive `match`es with no `_ =>` arm, so a new kind without a category does not compile.
- **Scaling.** Damage by the key Attribute; interval by DEX (`DEX_SPEED`, via `Scaled::per`); arc by DEX (`DEX_ARC`); range and projectile speed by STR (`STR_RANGE`). Push and projectile radius do not scale. `MeleeStats` and `RangedStats` store the numbers at `At { str, dex }`, the wielder's STR and DEX they hold at; `resolve_melee` and `resolve_ranged` give a `ResolvedWeapon`. A starter weapon's `At` is its class's start STR/DEX, an enemy weapon's is its stat block's, a sample item's is `At::BASE` (10, 10). The interval is stored in seconds (`cooldown`); the UI shows `1 / cooldown`.
- **Items** (`defs/items.rs`): `ItemId` and one `ItemDef` row per item in `items::def`: `name`, `sprite`, `base` (`ItemBase`: `Melee`, `Ranged`, `Armor`, `Ring`, `Shoes`, `Belt`; `Shield` is reserved, no item uses it), `classes` (never empty), `req` and `props`. A property is a `PropKind` plus `magical`: `DamageShare`, `OnHit`, `Light`, `Resist`, `Attr`, `EffectResist`, `Weight`, `MoveSpeed`, `MaxHp`. Rings, shoes and belts carry only magical properties.
- **Slots.** `EquipSlot` is Melee, Ranged, OffHand, Armor, Ring1, Ring2, Shoes, Belt; `Equipment` holds an `Option<ItemId>` for each. `Member.equipment` carries it into the run; `Progress` stores it (`Equipment::starter(class)` (`ClassDef.starter`) for a new character). An empty melee slot falls back to the class's starter melee weapon (every hero always has a melee weapon for the melee rule); an empty ranged slot means no ranged weapon, and a Ranged ability then cannot be used (`LoadoutError::NoWeapon`).
- **Rules.** `check_equip` and `check_equipment` refuse an item whose slot, class, requirement or proficiency does not fit. The slot check matches every `ItemBase` (no catch-all), so a new base must name its slot; the reserved `Shield` fits `OffHand`. Weapon and armor proficiencies are per class in `defs/classes.rs`. Armor is a maximum: Cloth < Light < Medium < Heavy, and a class wears its maximum and everything lighter (Wizard Cloth, Paladin Heavy, Barbarian Medium, Elven Ranger Light). `Requirement::Attr(attr, n)` (`defs/requirements.rs`) is checked against the Attributes without items (class + race + shop), so a ring cannot unlock the staff that unlocks the ring.
- **The sheet folds equipment in.** `hero_sheet(class, &Build)` first adds the armor bases (physical resistance, weight), then the properties: `Attr` points, resistances, effect resistances, weight, move speed, max HP. The Attributes with items then scale the weapons. `DamageShare` and `OnHit` are weapon-only: they go to their own weapon (index 0 melee, 1 ranged), so they ride only on that weapon's attacks (a flaming sword's heat on Sword and Axe, not on Holy Light or Fireball), and a data test refuses them on other items. An item has at most one `OnHit`. Added shares are scaled down so a split never passes 100 % (`DamageSplit::with_shares`). A hero carries the light of the item with the largest light radius, or `LightKind::Radiant` (radius 2) with that keystone, whichever is larger.
- **Enemies and races.** Enemy stat blocks in `defs/enemies.rs` point to enemy weapons (Goblin Bow, Rusty Sword, Skeleton Longbow, Cleaver, Orc Bow, Spiked Club, Mimic Bite, Imp Claws, Chort Claws) and `enemy_attacks_are_pinned` pins their numbers. Races in `defs/races.rs` carry natural weapons (Unarmed Strike, Bite, Claws, Beast Bite, Tail); they are part of the body and never go into a slot. Boss weapons are not defined: their scripts keep their constants.
- **Not built yet.** `PropKind::Aura` (it needs a per-tick area layer and an HP rule), the shield (see the "Shields" issue). Heroes are drawn with their equipped weapons and the equip UI is real (plan 5, §11a "The character screens").

**Abilities (progression plans 3a and 3b; spec §6.3–6.6).** Plan 3b added the 16 new abilities (ids 7 to 22) on the 3a framework; their table follows the 3a rules below.
- **Data.** `defs/abilities.rs`: `AbilityId` (declared with `listed_enum!`, ids 0..=22: `MagicMissile, Fireball, Strike, HolyLight, Charge, Shoot, SummonWolf`, then the 16 of plan 3b) and one `AbilityDef` row per id in `abilities::def`: `slot` (Primary or Secondary), `category`, `uses`, `ranged`, `req`, `shape`, `own`, `weapon_mult` and `classes` (whose own pool can hold it: the class start, or a tree unlock node). Every `match` over these enums is exhaustive, with no `_ =>` arm.
  - `AbilityCategory`: `WeaponAttack` (Strike, Shoot, Hurl, Volley, Smite, Flanking Thrust), `Technique` (Charge, Whirl, Poison Coat, War Cry, Ground Slam), `Spell` (Magic Missile, Fireball, Frost Shard, Chain Spark, Frost Nova, Haste), `Innate` (Holy Light, Summon Wolf, Judgement, Purify, Consecrate, Entangle). `abilities::governing(category)` returns `Option<(Attr, f64)>`, the Attribute that scales damage and is the power of damage-type effects, with the percentage each point moves that damage by: INT for spells, CHA for innate, `None` for weapon attacks and techniques (their numbers and power are the weapon's). The 3a `unreachable!` arm in `sheet.rs` is gone.
  - `Uses` says which weapon it strikes with: `Melee`, `Ranged` or `Nothing` (spells and innate abilities; a data test checks `Nothing` iff Spell or Innate).
  - `ranged` is the melee-rule flag: a ranged ability is a projectile or aimed at a distant spot. Magic Missile, Fireball, Shoot, Frost Shard, Chain Spark, Judgement, Hurl, Volley and Entangle are ranged; the others are not (so Entangle, aimed at a spot, is refused in melee like Fireball).
  - `shape`: Swing, Projectile, Blast, Ring, Dash, SelfArea, GroundArea, Buff, Summon (see "Shapes" below). `own` holds the numbers the ability does not take from a weapon (damage, cooldown, range, speed, radius, duration, projectile kind, the Attribute value `at` at which its damage is given, and from plan 3b `split: Option<DamageSplit>`, which wins over the projectile kind's split, and `effect: Option<OwnEffect>`); `weapon_mult` changes a weapon's numbers (`damage`, `time`, `arc`, and `share: Option<(DamageType, f64)>`, a damage-type share added to a weapon attack; Charge is damage 0.8). `OwnEffect { kind, power: Attr, look }` is the effect an area ability applies, at the power of that Attribute. `AbilityDef.behind` is the arc behind a target (radians; 0 = none) that doubles a melee hit. `weapon_mult.share` applies to Ranged weapon abilities too, though no ranged ability sets one.
  - `req` uses the same `Requirement` as items and tree nodes. Ability Attribute requirements count item points (like tree nodes, spec call 17, and unlike equip requirements): a ring that grants an ability is about access, so its own +INT may unlock it. A `WeaponKind` requirement is always checked against the weapon in the slot the ability uses.
- **Resolution** (`sheet::resolve_ability`, called by `hero_sheet` per pick) gives a `ResolvedAbility` (cooldown, damage, range, arc, speed, radius, duration, `pierce`, `pierce_through`, `ranged`, projectile, split, on-hit, power, `push`, `push_str`, `behind`, and `effect`, which is not exported):
  - `Uses::Melee`: damage = weapon damage × `weapon_mult.damage`; arc = `weapon_mult.arc` or the weapon's; range = the hero's reach (`HERO_REACH` 17 + `PLAYER_RADIUS` 5 = 22, `Sheet.reach`); split, on-hit, power and `push` from the weapon; `speed`, `radius` and `duration` from `own`.
  - `Uses::Ranged`: damage, range, projectile speed, radius, projectile kind, split, on-hit and power from the ranged weapon; `pierce = u8::MAX` (no limit) and `pierce_through` from the weapon's `PropKind::Pierce`. The Ranged slot being empty makes the ability unusable.
  - `Uses::Nothing`: its own numbers; damage scaled by the governing Attribute (`Scaled`, bit-exact at the class start); power = that Attribute, only if it deals damage.
  - **Cooldown (scope call 6):** `own.cooldown` if above 0 (Charge: 5 s), otherwise the weapon's interval × `weapon_mult.time`.
  - **Push (call 7):** a melee ability pushes with its weapon's `push`, at `push_str` = the hero's STR plus `PushStr` mods. Every starter weapon has push 0, so nothing moves at the start.
  - The skill tree: `hero_sheet` folds `Build.nodes` (`trees::gains`) in after the shop's `extra` and before items: resistances, proficiencies (`sheet::profs`), unlocks (pooled like `Build.own`), and per-ability improvements appended to the version's mods. The tree adds no Attribute points (the Attribute nodes were removed 2026-10-23; Attributes come only from class and race, the shop and items). The old `StatUpgrades` no longer reach the sheet; `Base.keystone_mult` (1.0 until the keystones) replaces `upgrade_mult`.
  - **Numbers at the class start equal today's**, except the deliberate changes of plan 3a: Charge damage 25.6 (was 25), the Barbarian's reach 22 (was 25), the ranger's fallback arc (the rapier's 1.0; unused by the single-target strike). `DAGGER_RANGE` and `DAGGER_COOLDOWN` are gone; the client reads `info.fallback`.

**The melee rule (spec §6.4).**
- **Heroes** (`run/abilities.rs`, `try_use`). `melee_targets(run, pi)` lists, nearest first, the monsters on the ground that are not allies and the closed chests within `sheet.reach` (a hidden mimic answers like a chest); `melee_target` is the first. This is "in melee".
  - A **ranged primary** (Magic Missile, Shoot) in melee becomes a **strike with the melee weapon** (`sheet.fallback`, the Strike numbers of the melee weapon: the Wizard hits with his staff, the Elven Ranger with her rapier). The cooldown is that weapon's own.
  - A **ranged secondary** (Fireball) does not fire in melee and spends no cooldown; the client shows a short "Too close" hint on the slot. Holy Light, Charge and Summon Wolf work in melee.
  - The strike hits the **nearest** target in any direction (no arc), like the old rapier thrust. If it kills, the rest of its damage (overkill formula below) goes to the next-nearest target in reach, and so on, stopping at a target it does not kill, an immune one, or a chest.
- **Enemies.** An enemy whose only attack is ranged has a melee `alt`; the AI's existing rule (a melee `alt` is used when the target is in its reach) does the rest. Archers and the Disciple punch (`UnarmedStrike`); the Necromancer and the Summoner strike with their staffs (`NecromancerStaff`, `SummonerStaff`, two enemy weapons used only by the melee rule). `enemy_attacks_are_pinned` and `enemy_melee_splits_are_unchanged` pin the numbers.

**Overkill piercing (spec §6.5).**
- A killing hit uses up only the damage needed to bring the target to 0 HP after its resistances: `used = hp_left / Σ(share_t × (1 − res_t))` (`damage::overkill_rest` returns the rest, or `None` for a non-kill or an immune target). The resistances are the target's current ones (the same as `hurt_monster` and `hurt_creature` use); a hero's armor counts. The rest flies on to the next enemy. A non-kill stops the shot, and so does an immune target.
- `Projectile.pierce` is a `Pierce` (`run/entities.rs`): `Never`, `Overkill { left }` (`u8::MAX` = no limit) or `Through { left, then }` (`left == u8::MAX` = passes every enemy and never counts down). `ResolvedAbility.pierce` is the overkill count (0 = stops at the first enemy, n = up to n more by overkill, `u8::MAX` = no limit) and `pierce_through` the through count (`u8::MAX` = no limit; mods saturate there). `Pierce::new(overkill, through)` builds it. The projectile remembers the ids it has hit.
- **Who pierces.** Shoot and enemy weapon shots (`pierce: true`) have no limit; spells have 0, unless a mod adds `Pierce(n)`.
- **Through-piercing** passes up to n enemies with full damage, killed or not, and then follows the overkill rule. It comes from a ranged weapon's `PropKind::Pierce(n)` (sample: `HuntersBow`, Elven Ranger, `Pierce(2)`, not magical) or from `AbilityMod::PierceThrough(n)`.
- **Client.** `GameScene` keeps a cosmetic copy of the shot. `export.rs` sends each enemy kind's max HP and damage resistances (`ENEMY_KINDS` in `defs.ts`), a snapshot entity carries its HP as a byte share of its max, so the client estimates `hp = share × max_hp` and runs the same formula (`cosmeticPierce` in `game/world.ts`). A shot that predicts a kill flies on; otherwise it ends at the enemy. When the guess is wrong the shot never jumps back: a predicted kill that did not happen flies on a few px until the server's shot is gone, then vanishes; the spark at the enemy where the server stopped it is the one its `Dmg` event draws (the cosmetic shot draws none of its own, which used to double it). If the server's shot never showed up in a snapshot at all (it hit within the first ticks), a shot that predicted a pass vanishes once it is older than `unseenShotLimit` (round trip + interpolation delay + 0.15 s, `world.ts`) instead of flying its full range. A predicted stop remembers where the cosmetic shot touched the enemy (`stoppedShots`), and the server's projectile stays hidden until both its interpolated (drawn) position and its newest snapshot position are past that enemy; then it is taken out of `stoppedShots` and `endedShots` and drawn from there on. So it reappears past the enemy, never before it, after a short hidden gap. An exact kill (a rest of at most `OVERKILL_EPS`) stops the shot on both sides. Kinds shared by two enemy types use the normal type's max HP, so a mismatch is only cosmetic.

**Loadouts and item-granted abilities (`defs/loadout.rs`).**
- **Build.** `Build { extra, nodes, equipment, loadout, own }` is everything a hero brings besides the class; `Build::start(class)` is the class start. `Loadout { primary: Pick, secondary: Pick }`, `Pick { ability, source }`, `Source::Own` (the hero's pool) or `Source::Item(EquipSlot)` (the version the item in that slot grants). `hero_sheet(class, &Build) -> Result<Sheet, LoadoutError>`.
- **The pool.** `Own` holds the class's two starting abilities plus `Build.own` (the debug pool; the tree's unlock nodes are folded in from `Build.nodes`), and only abilities whose `classes` list the class. An item grants an ability with `PropKind::GrantAbility { id, mods, waive_attrs }`; the ability must then be picked with that item's `Source::Item(slot)`.
- **Versions.** The same ability can be offered by several sources, each as its own version: the class's own, or a worn item's with that item's `AbilityMod`s. A pick names the version; `pick_version` returns its mods and whether it waives the Attribute requirements (`waive_attrs`; the weapon-kind requirement is never waived). Samples: `RingOfTheMagus` (Magic Missile, `DamageMul(0.75)`, waives Attributes) and `SeekersBand` (Magic Missile, `Pierce(1)`, does not waive). `Sheet.wolf` (`WolfMods`) holds the Summon Wolf version's `CompanionHpMul` and `CompanionDashCooldownAdd`.
- **`AbilityMod` stacking** (`apply_mods`): additions (`Pierce`, `PierceThrough`, `DurationAdd`, `CooldownAdd`, `PushStr`, `AddShare`, `BehindArc`) are summed and multipliers (`RadiusMul`, `RangeMul`, `DamageMul`, `ArcMul`) multiplied, each in a sorted order so the result never depends on the order of the mods. `AddShare` takes only non-physical types (`DamageSplit::with_shares`). Results are clamped: damage, radius, range, arc and duration never go below 0, and a cooldown moved by `CooldownAdd` never below `MIN_COOLDOWN` (0.05 s). Mods of different versions never mix: each pick has only its own version's mods.
- **Errors.** `LoadoutError`: `Equip(slot, EquipError)`, `NotInPool`, `WrongSlot`, `Requirement(ability, req)`, `NoWeapon(ability, slot)`. `message()` gives the text the player reads. `check_pick` runs the requirements (item points counted, `waive_attrs` skips the Attribute ones).
- **Where it is checked.** `hero_sheet` first checks the equipment against the Attributes without items, then each pick. Ready and Start in the lobby validate through `hero_sheet`, so a bad loadout is refused with the error's message. `lobby.rs` builds each member's `Build` from the saved `Progress::build` (the debug picks on top).
- **`DebugLoadout { primary, secondary }`** (`ClientMsg`, debug accounts only; in a debug room, not Ready, no run running). It sets any ability of your class (the debug pool = the abilities whose `classes` list it), from `Own` or a worn item. It skips the "unlocked" check but keeps the Attribute and weapon checks. The waiting room has a plain DOM picker, shown only when `Welcome.debug` is set. It stays as the debug flag on top of the real build (Ruling 13); `SetLoadout` is the real path.

**How to add an ability.**
1. An `AbilityId` with the next id (the compiler asks for every `match`; every shape executor lists every id, so add it to the `unreachable!` arm of each executor that does not run it) and one row in `abilities::def`: slot, category, `uses`, `ranged`, `shape`, `own` numbers (`split`, `effect` and the Attribute `at`) or `weapon_mult` (`share`), `behind`, `classes`, `req`. Take the design rule into account: primaries are dependable damage with at most a mild effect, strong control goes on secondaries with long cooldowns. The data test `ability_data_is_consistent` checks the rules.
2. Its executor: an arm in the executor of its shape (`use_projectile`, `melee_arc`, `use_ring`, `use_self_area`, `use_ground_area`, `use_buff`, ...; a new shape is one more arm in `try_use`) reading the numbers from the `ResolvedAbility` only. A weapon-based ability builds its damage with `weapon_damage` so Poison Coat applies. A ground area with a lasting effect is a hazard (`spawn_hazard` with a `HazardSide` and a `HazardPulse`). A new `AbilityMod` needs an arm in `apply_mods` (exhaustive).
3. Its mods and grants: an item with `PropKind::GrantAbility`, or the class pool.
4. Client: run `cargo test` (it regenerates `ABILITIES` in `defs.ts`, which the HUD and the picker read), then add the prediction in `GameScene.predictAbility` (by shape; a new shape fails to compile there), its drawing (a projectile in `PROJECTILES`, a hazard kind in `isHazardKind`/`drawHazard`, a `Boom` code or an event) and, to try it, pick it with the debug row of a debug account (`DebugLoadout`, `DebugEquip`).
5. Tests: a resolution test (class start numbers), a melee-rule test if `ranged`, and a `hero_sheet` test for the version if an item grants it.

**How to add a weapon.**
1. If it is a new kind, add it to `WeaponKind` (next id) and to `category()`; the compiler then asks for nothing more. Add a sprite or none.
2. Add an `ItemId` and one row in `items::def`: `melee(...)` or `ranged(...)` with its numbers and the `At` they hold at (`At::BASE` for a new sample weapon), `classes`, `req` and `props` (`DamageShare`, `OnHit`, `Light` are the weapon properties).
3. Add the proficiency in `defs/classes.rs` if a class should wield the kind. Natural weapons go on a race, not in a slot.
4. `cargo test`: the data tests check the rules (non-empty `classes`, weapon-only properties, sprites in the atlas, the listed numbers).

**How to add an item.** One `ItemDef` row in `items::def` plus its `ItemId`:
1. Armor, ring, shoes or belt: pick the `ItemBase`; armor takes `armor(class, physical, weight)`; rings, shoes and belts carry only `mag!` properties.
2. `req` holds Attribute requirements; `classes` lists who may wear it (never empty; `ALL` for everyone).
3. `item_data_follows_the_rules` checks every item automatically (classes, requirements, property rules).
4. Add the item to the data tests' expected numbers if it needs pinning (`items_carry_the_listed_numbers`).

**Attribute shop, skill trees and keystones (progression plan 4; spec §9 to §12).**
- **Attribute shop.** `BuyAttribute` raises `Progress.bought` by one. The price is `attr_price(a, current)` = `(100 + 25 × max(0, current − 10)) × weight`, rounded, with `current` the Attribute without items (class, race and shop; items never raise the price) and `ATTR_WEIGHT` STR 1, DEX 1.25, CON 1, INT 1, WIL 0.8, CHA 1. `CharacterInfo.prices` carries the next price of each.
- **Trees as data** (`defs/trees.rs`). `NodeId` is generated (`W0`, `WA2`, … per class; names keep their spec ids, so there are gaps; 63 nodes, one free start node per class) and `trees::def(id) -> NodeDef { class, pos, kind, name, text, cost, req, links }`, an exhaustive `match`. `NodeKind`: `Start`, `Unlock(ability)`, `Improve(ability, AbilityMod)`, `Proficiency(Prof)`, `Resist(type, fraction)`, `Keystone(Keystone)`. `links` are undirected (`neighbours`). `check_buy(class, owned, node, attrs_with_items)` allows a node when it is the class's, unowned, next to an owned node (or the start), and its `req` holds against the Attributes **with** items (like ability requirements). `Progress::buy_node` then spends the XP; `nodes` is kept sorted and never holds the start. `trees::gains(&nodes)` folds the owned nodes into `TreeGains` (resistances, proficiencies, unlocks, per-ability improvements, `KeystoneSet`).
- **What the sheet does with it.** `hero_sheet` adds the shop (`Build.extra`) to the class and race points, then the tree's resistances and proficiencies (`sheet::profs`, used by `check_equip`), pools the unlocks with `Build.own`, and appends an `Improve` to the mods of the equipped version of that ability, whatever its source (Ruling 1: it stacks with the item's mods by the same add-then-multiply rule, and it is dropped while the ability is not picked). `Sheet.armor` is gone: armor is only the armor item's physical resistance and weight (the rules log has no armor step).
- **Keystones** (12, one per class tree end, `Keystone` generated with `KeystoneSet` as a bit set). Static ones are folded in `hero_sheet`; run-time ones live in `run/keystones.rs`.

  | Keystone | Class | Effect |
  |---|---|---|
  | Arcane Overflow | Wizard | Spell damage +15 %, spell cooldowns +10 % (static: `Base.keystone_mult`, cooldown) |
  | Deep Winter | Wizard | Hit × `(1 + 0.2 × cold share)` on a Chilled or Frozen target (Ruling 4) |
  | Pyromancer | Wizard | Hit × `(1 + 0.2 × heat share − 0.2 × cold share)` (Ruling 4; static in `Base.keystone_mult`) |
  | Radiant | Paladin | Innate abilities × 1.2 against targets whose races include Undead or Demon (Ruling 7); light `LightKind::Radiant` (radius 2, 0xffe890, 0.6, flicker 0.05) |
  | Unshaken | Paladin | Sleep effect resistance +100 % |
  | Bulwark | Paladin | Armor weighs half; +10 % physical resistance |
  | Berserker | Barbarian | Below 50 % HP (`berserk`): damage × 1.25, a cooldown started then ÷ 1.25, every resistance −0.10, also below 0 (Ruling 5); the client gets the cooldown factor as `SelfState.cd_mul` |
  | Juggernaut | Barbarian | Weight +4; Slowed, Chilled and Entangled resistance +100 % |
  | Unbreakable | Barbarian | `Sheet::save(Attr::Con)` counts +4 (`UNBREAKABLE_CON`); HP, speed and prices do not change (Ruling 2) |
  | Pack Hunter | Elven Ranger | Targets the wolf bit in the last 2 s (`Monster.wolf_bit`, `BITE_MARK_SECS`) take × 1.2 from the hero |
  | Deadeye | Elven Ranger | × 2 for hits of an ability with `ranged: true` on a target with Slowed, Chilled, Entangled or Sleep (Ruling 6) |
  | Venomancer | Elven Ranger | × 1.15 on Poisoned targets |

  `keystones::on_hit(run, mi, dmg)` is called from `hurt_monster`: it applies the factors of `keystones::outgoing` and records each as `Mult::Keystone(k, f)` in the hit's `why` while a slot is free. Only the hero's own hits count (Ruling 3): `why.by` is the hero's entity id and the hit is not an effect tick, so the wolf's bites and DoT ticks are not "you". **Overkill carry and Chain Spark jumps use the amount before the run-time keystones**, so they do not compound (the carried rest is computed from the hit's own resolved damage).
- **`Progress` v2.** `Progress{version: 2, rev, xp, total_xp, coins, bought, nodes, xp_spent, equipment, inventory, loadout}`. `from_json` is lenient (Ruling 12): unknown node, item or ability ids are dropped one by one with a `tracing::warn!` and the rest stays; only a document that is not an object at all starts fresh, and so does one whose core number field (`version`, `rev`, `xp`, `total_xp`, `coins`, `xp_spent`) is not a number (both are logged as errors). A version-1 document (flat `upgrades`) is converted once: every bought level is refunded as XP at the old price (`100 + 75 × level`, capped at level 10) and the result is saved as version 2. Equipment: the class starters for a new character, `inventory` starts empty, `loadout` is `Loadout::start(class)`.
- **Respec** (`Progress::respec`): costs `RESPEC_BASE` 20 coins plus 1 per `RESPEC_PER` 50 XP spent (`respec_price`, also in `CharacterInfo`). It refunds `xp_spent` as XP, clears `bought` and `nodes`, resets the loadout to the class start, and moves every worn item that no longer passes `check_equip` into the inventory (Ruling 11). Items are never lost.
- **Equip and loadout.** `Equip{slot, item}` takes one copy out of the inventory into the slot and puts the old item back; `item: None` moves the slot's item to the inventory (Ruling 10). An empty Melee slot still plays with the class starter. `SetLoadout` stores any pick whose ability fits its slot (Ruling 9); locked, missing-weapon and requirement problems show in `sheet.loadout_error` and are refused at Ready and Start.
- **Debug.** The debug flag stays (Ruling 13): `DebugLoadout` and `DebugEquip` keep the whole class pool and the Attribute lift, now on top of the real build, for debug accounts in debug rooms; debug runs bank (#151). A debug weapon is a per-slot override (`Conn.debug_touched[slot]`): a slot never touched in debug plays the saved weapon, a touched one plays the debug choice (starter, item or empty). `DebugGrantItem` fills the inventory. A real `SetLoadout` replaces the debug picks: the server clears `Conn.loadout` and `Conn.debug_loadout` (the waiting room's debug row then shows the new picks).
- **Admin.** "Upgrades bought" is "tree nodes bought" (`jsonb_array_length(progress->'nodes')`; Ruling 14).
- **Client.** `generated/progression.ts` (written by `export.rs`) carries the static data: nodes with their links, keystone texts, Attribute effect texts, `ABILITY_INFO` and `ITEMS` (below). The screens are described in "The character screens".

**The character screens** (plan 5; the `?uidemo` spike and the temporary panel `ui/progressPanel.ts` are gone).
- **Flow.** Login (`ui/auth.ts`, unchanged), then the roster (`ui/roster.ts`: one card per character with its figure holding the equipped weapon, plus "New character" and the account controls). A click on a card connects the WebSocket (once), selects the character and opens its hub on the Sheet tab. "New character" opens `ui/create.ts` (`#create-back` goes back); creating a character opens its hub. The hub has "< Roster" and "To the dungeon", which opens the runs list. The runs list has "< Character" back to the hub. `Hub.setCharacter` ignores a `Character` message for any id other than the selected one, so a late message for the old character never draws under the new header. `net.onClose` shows its message on the hub too.
- **Look (UI polish).** One palette as CSS tokens on `:root` in `style.css` (`--bg #0f090e`, `--panel #221620`, `--panel-edge #5a3a4a`, `--text #f0e6d8`, `--muted #b3a3a8`, `--gold #e8c040`, `--red`, `--green`, `--faint`, `--well`, `--gold-deep`, `--gold-ink`, `--edge-soft`) and "leather and brass" controls: buttons `button.primary` (gold), `.danger`, `.ghost`; padding 5 x 10, radius 6 px; tabs 7 x 12; fields and selects 10 x 12, radius 8 px; disabled at 0.4 opacity; every control has a gold focus ring; `.check` for checkboxes and `.panel` for boxes. Headings use IM Fell English SC, everything else Inter. The sheet fits 1280 x 720 without scrolling.
- **Files.** `ui/hub/hub.ts` (header with XP and coins, the four tabs, one render function per tab, the error line), `sheet.ts` (Attributes with the buy buttons and rising prices, derived values, resistances, proficiencies, keystones, respec), `tree.ts` (the node graph per class, legend, buy after a confirm), `equipment.ts` (paper doll, inventory), `loadout.ts` (the two slot lists), `tip.ts` (tooltips), `model.ts` (pure helpers: `nodeState`, `blockReason`, `slotForItem`, `itemProblem`, `poolFor`, `abilityNumbers`, `attrEffect`), `fixture.ts` (test data). Also `ui/icons.ts` (ability icons as a placeholder of two letters on the main damage-type colour, item icons from the item's atlas frame, or letters in a box when the sprite is `""`), `ui/classes.ts` (`figureWeapon`) and `ui/screens.css`.
- **No optimistic state.** Every build change goes over the WebSocket (`BuyAttribute`, `BuyNode`, `Respec`, `Equip`, `SetLoadout`, `DebugGrantItem`). The answer is a `Character` message, or an `Error`. `Hub.error` only writes its line and never redraws, so typed input stays. Every render first removes all `.ui-tip` elements from `document.body`, so a tooltip never outlives a `Character` message or a tab switch.
- **The client never blocks a pick or Ready by its own rules.** An invalid choice is shown red with the reason and a hint, but it stays clickable and the server refuses it with the same reason, which the client shows.
- **Equipment (Ruling 5).** Clicking an inventory item equips it into its slot (`slotForItem`: a ring goes to the first empty ring slot, else Ring1). Clicking a worn item takes it off. Dragging an inventory item onto a slot equips it there; dragging a worn item onto the inventory takes it off. Red items (not proficient, or a requirement is not met) can still be tried. The inventory grid shows at least 20 cells and grows in rows of 5; duplicates are separate cells. The "From items" line under the doll is the Attribute points from items (`AttrLine.items`) plus the non-Attribute properties of each worn non-weapon item, once per worn item, with no string de-duplication (two identical rings count twice; the Attribute grants are already in the points).
- **`PoolCard` and the loadout (Ruling 1).** `sheet::pool_cards(class, &Build)` returns one `PoolCard{pick, ability: Option<ResolvedAbility>, error: Option<String>, locked}` per ability the hero could slot, in this order: the class start primary and secondary, `b.own`, owned tree unlocks (node order), item versions (slot order), then the locked tree unlocks. `ability` has the numbers for this hero (version mods and tree improvements applied; locked cards have base numbers only; `None` when the weapon it uses is missing). `error` is `LoadoutError::message`. `SheetSummary.pool` carries the cards, so the client keeps no pool of its own. The Loadout tab lists them per slot, the tree tooltips for locked unlocks use the same cards. A saved pick that is no longer in the pool shows first as "(unavailable)" with the line "Not available any more.", and changing the other slot does not overwrite it.
- **The export of texts (Rulings 2 and 3).** Ability descriptions come from `abilities::text(id)`, exported as `ABILITY_INFO{category, uses, req, text, tint}`. Item texts come from `items::base_text` and `items::prop_text`, exported with the weapon kind, proficiency (`sheet::item_prof`), sprite and requirement as `ITEMS`. The client only lays them out (`ui/text.ts` `CLASS_TEXT` keeps just the title and blurb). Weapon kinds are spaced in `requirement_text` ("Duelling Sword"). A ring that waives Attribute needs reads "(ignores its Attribute needs)".
- **The waiting room (Ruling 7).** Your own party row has two `<select>`s (`data-own="Primary"` and `"Secondary"`) listing the non-locked pool cards of the slot; an invalid one reads "Frost Nova (needs INT 17.)" (`pickOptionLabel`). They show while you are not Ready (the host: until the run starts). A change sends `SetLoadout`. `Lobby.error` redraws only for a refused build change (`isBuildRefusal`), never for an unrelated error. For a debug account the debug row stays (it is the only place for debug controls besides the hub's Grant select).
- **Weapons in the run (Rulings 8 and 9).** `PlayerInfo` has `melee: ItemId` (the worn melee weapon, or the class starter) and `ranged: Option<ItemId>`, filled from `Player.weapons` in `run/entities.rs` (a `Player` has no build, so the weapons are copied in when the hero is made). Ranger-style figures (`attack: 'ranged'` in `anim/defs.ts`, `heroWeapons`) hold the ranged weapon's sprite and thrust with the melee one; a Ranger without a ranged weapon holds the melee sprite for both. Other classes hold the melee weapon's sprite; their ranged weapon is not drawn. The mount (`blade`, `staff`, `bow`) stays the class's. The roster and hub figures use the same rule (`figureWeapon(info)`).
- **Tests.** Vitest for the model, tree, equipment, loadout, hub and roster logic; the smoke test (`tools/e2e/smoke.mjs`) opens all four hub tabs and checks that the tree shows an owned node (`hub: four tabs shown`), then the waiting-room picker before and after Ready, and takes `0-hub-*.png` and `3-weapons.png` (the heroes after the first move).

**How to add a tree node.** One `NodeId` variant (declared with `listed_enum!` in `defs/trees.rs`, next id) and one arm in `trees::def`: class, grid `pos`, `kind` (of the existing kinds: nothing else changes), `name`, `text`, `cost`, `req` and `links` to a neighbour (a link joins both ways). The data tests check that every non-start node is reachable from its start, that links stay inside the class and that the costs and requirements are sane. The client needs nothing: the Skill tree tab draws from `progression.ts`. Run the docker suite so the generated files are rewritten and commit them.

**How to add a keystone.** (1) A `Keystone` variant with the next id (a compiler error lists every `match` over it: `keystones::name`, the node kind). (2) A node with `NodeKind::Keystone(k)`. (3) A static effect goes in `hero_sheet` (`ks.has(...)`, like Bulwark) or in `Base.keystone_mult`; a run-time effect is a factor in `keystones::outgoing` (hits) or a rule in `keystones.rs` (like `berserk`). (4) Add its line to the table above and to the rules-log text if it is a new factor kind (`Mult::Keystone` already prints its name and factor). (5) A test in `sheet.rs` or `keystones.rs`.

**Tamper safety.** The server is authoritative.
- Everything the client gets (`Me`, `Character`) is for display only.
- No message carries progress values from the client to the server.
- The client can only ask for actions (select, buy), and the server checks them against the database.

**Scaling later** (nothing built for it yet):
- The database is only touched at login, WebSocket connect, character select, purchases and run end; everything per tick stays in RAM. 10,000 players in 10-minute runs would bank about 17 times a second, so no cache is needed in front of PostgreSQL.
- The real limits of one server are CPU (the 60 Hz simulations), the single lobby mutex and bandwidth. The answer to those is several game servers.
- Only then is an in-memory store such as Valkey (BSD-3) worth adding. It would hold presence (one connection per account across servers), the shared run list and pub/sub between servers. It should not be a write-behind cache for progress, which would risk losing data and create two sources of truth.
- All queries are in `db.rs`, so such a change stays local.

## 11b. Admin area and statistics

**Look (UI polish).** The admin page is dark only and uses the game's palette and fonts (`admin/admin.css` imports `fonts.css` and copies the `:root` tokens; the old light and dark admin themes are gone). Links and summaries have the gold focus ring. The admin shots of the smoke test are the dark page only.

**Page.** `/admin` serves `client/admin.html`, a second Vite entry with its own code in `client/src/admin/` (plain DOM, no Phaser). Views are picked by the URL hash: `#/` dashboard, `#/players`, `#/players/<id>`, `#/audit`. Every player-chosen string is inserted as a text node (`dom.ts` `h()`), never as HTML.

**Login (`admin.rs`, `auth::AdminLogin`).**
- The admin is not a game account. The name and password come from `ADMIN_USER` and `ADMIN_PASSWORD`; only their SHA-256 digests are kept, and both are compared in constant time.
- Without both variables, or with a password under 12 characters (`ADMIN_PASSWORD_MIN`), every `/api/admin/*` route answers 404 and the server logs why at start-up.
- Throttling: 5 failed admin logins per IP and 20 in total per 5 minutes give a 429. A failed login is logged without the IP.
- **Sessions:**
  - The token format is the same signed one as the players' (`Auth::new_admin_session`), with a 12-hour hard limit (`ADMIN_TOKEN_MAX_SECS`).
  - **Idle timeout:** a session ends after `ADMIN_SESSION_MINUTES` (default 10, 1–1440) without an admin action. Every admin request restarts the clock (`AdminState::touch`) except the dashboard's automatic refresh, which sends `X-Admin-Background: 1` and only checks the session, so an open tab still times out. The page then asks for the login again.
  - Player sessions work the same way, with a 7-day default (`PLAYER_SESSION_MINUTES`, §11a).
  - The cookie is `ta_admin` (HttpOnly, SameSite=Strict, `Path=/api/admin`, `Secure` with `COOKIE_SECURE`). It has no Max-Age, so it is gone when the browser closes.
  - Admin sessions live in memory (`AdminState.sessions`), so a restart logs the admin out.
  - A player's `ta_session` cookie never grants admin access.
- State changes must be JSON (`api::require_json`), like the player API.

**Admin API (`/api/admin`, ts-rs types in `stats.rs` and `admin.rs`).**

| Request | Effect |
|---|---|
| `POST /login {name, password}` | Sets `ta_admin`. Answers `AdminMe{name}`. The same 401 for a wrong name and a wrong password. |
| `POST /logout {}` | Ends the admin session and clears the cookie. |
| `GET /me` | `AdminMe`, or 401 (404 when the area is disabled). |
| `GET /stats` | `AdminStats` (below). |
| `GET /players?q=&sort=name\|created\|active&page=` | `PlayerPage`: 50 per page, `q` matches anywhere in the name (`_` and `%` literally). |
| `GET /players/{id}` | `PlayerDetail`: account, characters (with "playing now"), activity, the last 10 runs. |
| `POST /players/{id}/password {password}` | Player password rules. Sets the hash, deletes all sessions of the account in the same transaction, closes its WebSocket. |
| `POST /players/{id}/debug {debug}` | Marks or unmarks a debug account (`db::set_account_debug`). Unmarking wipes the progress of every character of the account in the same transaction; the account's WebSocket is closed after the commit. Audit rows `set_debug` / `clear_debug` (with the number of wiped characters). A request that matches the current flag (a stale admin tab) changes nothing: no wipe, no kick, no audit row. The admin page shows a "Debug" badge in the list and on the player page; unmarking sits behind typing the player's name. |
| `DELETE /players/{id}` | Closes its WebSocket, deletes the account (cascade: sessions, characters). |
| `DELETE /characters/{id}` | Any account's character. Whoever plays it is logged out first, then it is deleted and forgotten by the lobby. |
| `GET /actions` | The last 100 audit rows. |

Every change writes a row to `admin_actions` (admin, action, target name at that time, detail) and counts `ta.admin.actions`.

**Tracking (migrations `0002_admin_stats.sql`, `0003_run_players_left.sql`, `0004_runs_level.sql`).**
- `activity_days(account_id, day)`: one row per account and UTC day, written at login, registration and WebSocket connect (`db::touch_activity`, `ON CONFLICT DO NOTHING`). "Active players" means accounts that logged in or connected.
- `runs` + `run_players`: every ended run (`victory`, `defeat` or `abandoned` = everyone left) with level, boss (`NULL` for a level without one; 0004 made it nullable and added `level`, default `'Dungeon'` for older rows), length, party size and per player the class, kills, damage, healing, XP, coins, `survived` and `left_run`.
  - Leaving a dungeon counts as dying inside the game (`Player.alive = false`). `Player.left` keeps it apart, so the statistics count deaths as `NOT survived AND NOT left_run`.
  - Debug runs are stored with `debug = true` and left out of every run statistic. The statistics that sum over characters (total XP and coins, characters per class, tree-node levels, the top 10) leave out characters of debug accounts; account counts and active players still count debug accounts (they count logins).
- These tables have **no foreign keys** to accounts or characters. When an account is deleted its name goes with it and only an anonymous id stays, so past counts do not change.
- History starts empty when this is first deployed; the dashboard says so.

**Statistics (`stats::overview`).**
- Calendar days in UTC: "today" starts at 00:00 UTC, "7 days" is today and the six days before.
- **Live:** from `Lobby::live()` (online, in a dungeon, in the lobby, rooms waiting, dungeons running, and who is online with which character), plus account names from the database.
- **Totals:** accounts, characters, XP ever earned, unspent coins, runs.
- **Today / 7 / 30 days:** active players, new accounts, runs (won, lost, left), win rate over finished runs, average length and party size, kills, deaths.
- **Per level and per class** (30 days; "Levels" lists each level with its boss, e.g. "Dungeon – Demon", from `AdminStats.level_runs`; `AdminStats.levels` is the tree-nodes histogram), characters by number of tree nodes bought, the top 10 characters by XP earned, and 30 daily points of active players, new accounts and runs (won vs. the rest).
- Charts are hand-written SVG (`charts.ts`), drawn at the container's pixel width. Each has a hover and keyboard tooltip and a "Show as table" view.

## 11c. OpenTelemetry

`telemetry::init()` (first thing in `main`) always sets up the console log (`RUST_LOG`, default `info`). It also exports over **OTLP/HTTP (protobuf)**, but only when `OTEL_EXPORTER_OTLP_ENDPOINT` (or a per-signal endpoint) is set.

- **Endpoint:** the exporter appends `/v1/traces`, `/v1/logs` and `/v1/metrics` and honours the standard `OTEL_*` variables (`OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, …). `OTEL_SERVICE_NAME` defaults to `tiny-adventurers-server`.
- **No TLS:** no TLS client is compiled in, so the endpoint must be plain `http://`, typically a collector on the same Docker network. For HTTPS, enable the `reqwest-rustls` feature of `opentelemetry-otlp`.
- **ClickStack:** point the endpoint at its OTel collector, e.g. `http://otel-collector:4318`. Add the game to that network or publish the collector's 4318 port, and pass `OTEL_EXPORTER_OTLP_HEADERS=authorization=<ingestion key>` if the collector requires one.
- **Shutdown:** on Ctrl-C or SIGTERM the server stops and flushes what is still buffered (`Guard::shutdown`).

**Traces** (`tracing` spans bridged by `tracing-opentelemetry`):
- `http`: one span per request, named by the matched route and recording the status. Cookies and bodies are not recorded.
- `ws`: one span per WebSocket session, with the account id.
- `run`: one span per run, with the run id, level, boss, player count and outcome.
- One span per `db.rs` function (`#[tracing::instrument(skip_all)]`) and per admin query in `stats.rs`.

**Logs:** every `tracing` event at `info` and above becomes an OTLP log record, correlated with its span. The exporter's own HTTP client crates are filtered out (`OTEL_FILTER`) to avoid a feedback loop.

**Metrics** (every 15 s; attributes carry ids, classes, levels, bosses and outcomes, never player names):

| Instrument | Type | Attributes |
|---|---|---|
| `ta.players.online` | gauge, read from the lobby | `state` = lobby / in_run |
| `ta.runs.active` | gauge | `state` = running / waiting |
| `ta.logins` | counter | `result` = ok / fail / throttled |
| `ta.registrations` | counter | – |
| `ta.runs.finished` | counter | `level`, `boss` (only when the level has one), `outcome`, `debug` |
| `ta.run.duration` (s), `ta.run.players` | histograms | `level`, `boss`, `outcome` / – |
| `ta.player.deaths`, `ta.enemies.killed`, `ta.xp.banked`, `ta.coins.banked` | counters | `class` |
| `ta.tick.duration` (ms) | histogram, every server tick | – |
| `ta.ws.connections` | up-down counter | – |
| `ta.admin.actions` | counter | `action` |

Debug runs only count in `ta.runs.finished{debug=true}`.

**Trying it locally:**
1. Run a throwaway collector that prints what it receives (`otel/opentelemetry-collector` with an `otlp` HTTP receiver on 4318 and the `debug` exporter) on the compose network (`--network tinyadventurers_default --name otel-check`).
2. Start the game with `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-check:4318`.
3. Play, then read `docker logs otel-check`.

## 11d. Rules log

A toggleable text log that tells the player why a hit was 9 and not 12 and why an effect did or did not take. Design: `docs/superpowers/specs/2026-10-21-rules-log-design.md`. It is built to be removable: it lives in two folders and the game reaches it through a fixed list of one-line hooks, pinned by a boundary test on each side.

### The two folders

- `server/src/run/rules_log/`: `mod.rs` (the hook functions, `RulesLog` state on `Run`, the facts structs), `record.rs` (`LogRec`, `LineKind`, `Seen`/`Unseen`: what is kept until the snapshot), `text.rs` (all wording and number formatting), `tags.rs` (creature numbering), `send.rs` (the per-viewer filter, `LogW`/`LineW`, the byte cap), `tests.rs` (including the boundary test).
- `client/src/rulesLog/`: `index.ts` (`RulesLog`: keys, opt-in message, ties it together), `buffer.ts` (the last 300 records; `push` returns what to append and how many to trim), `prefs.ts` (localStorage `ta.rulesLog`), `panel.ts` + `rulesLog.css` (the DOM panel, bottom-left, Inter 11 px with tabular digits; inserted before `#ui`, so the pause menu and end screen paint over it), `tags.ts` (the tag texts above figures), tests including `boundary.test.ts`.

### How it works

- **Opt-in.** The client sends `ClientMsg::RulesLog { on, details }` (on `L` / `Shift+L`, and once at the start of a run if the saved prefs say on). `main.rs` forwards it to the run, which stores it per player (`set_prefs`). `rules_log::on(run)` is false when nobody has the log on: every hook returns at once, nothing is recorded and `Snapshot.log` is `None`.
- **Recording.** The hooks sit inside the game's own computations (`hurt_player`, `hurt_monster`, `Run::apply`, `heal_*`, the ability executors) and are handed facts the game already computed; they never mutate the game. The six fingerprint tests pass unchanged with the log on and off.
- **Visibility rule.** A record is sent to a player only if that player sees every creature it names at that moment (party members always count as seen; a gone creature never does, so the record is unseeable). Otherwise it is dropped, except damage the viewer (or their wolf) took: that gives the record's short `unseen` line, with the viewer's own resistance steps and no attacker data. An Immune or Healed hit from something unseen gives no line. An effect that rides on a hit from something unseen adds only its name to the short line ("… from something unseen · Chilled"), never a detail line (Ruling 11): the details carry the attacker's power. A pure effect hit (no damage: the lich's Sleep orb) carries its attacker as the record's origin (`hit_effect_by`), so it is judged like any record and a hero is not told about an unseen attacker's effect. A hidden mimic is tagged and named as a chest until it is revealed. A spectator gets what the spectated hero gets.
- **The cap.** `LOG_BYTES_PER_SNAP` = 4096 text bytes per snapshot; the rest is summed up in a closing note ("… n more records (log limit)"; it counts records, not their detail lines). The client keeps the last 300 records and its panel is append-only: a snapshot adds its rows at the bottom and trims the top beyond the cap; only a details toggle or a clear rebuilds it. With details off the server does not send the detail lines at all. **Bandwidth bound:** at most about 4 KB of text per snapshot and listener, so about 4 KB × snapshots per second (30) per player with the log on, in the worst case; with the log off nothing is sent.
- **Text.** All wording is in `text.rs`; the client formats nothing. A line is `LineW(time, kind, headline, details)`. Numbers are rounded to one decimal; multipliers show two (×0.49). Effect lines are details of their hit, with a headline suffix (" · Chilled").
- **Tags.** `tags.rs` numbers each creature once at spawn, per name ("Goblin 3"), as a plain counter whether or not the log is on, so numbers stay stable when someone turns it on mid-run. The snapshot carries `[entity, kind, number]` for the sent entities; `TAG_NAME` in the generated `defs.ts` gives the names. The client draws the tags above the figures only while the log is on, at the text resolution zoom x camera zoom x devicePixelRatio so they are sharp at the screen's real pixels (the world texts use the fixed `TEXT_RESOLUTION` instead, see §9).
- **Wire.** `Snapshot.log: Option<LogW>` is the eleventh element of `SnapW`. A hand-written `Serialize` for `SnapW` in `wire.rs` writes 10 elements while the log is off and 11 while it is on (serde cannot skip a trailing tuple field). This code is log-only but outside the module and not counted by the boundary test. The generated `SnapW.ts` types the 11th element as `LogW | null` although it is absent while off; `client/src/wire.ts` uses `w[10] ?? null`.

## 13. Known limitations

- Pack art gaps: no attack frames, no up/down facing. (The dragon, the demon and the lich have their own frames.)
- No sound.
- Damage types, resistances and the barrel numbers are first guesses for the balancing pass, and the user has not played the barrels yet (see the `balancing` issues).
- Lighting: all numbers (radius, intensity, flicker per kind, `TORCH_SPACING`, `DARK_SHARE`, `MIN_LIT`, `WARM`, the falloff edge, `BLAST_FLASH`, `HOLY_FLASH`) are first guesses for the balancing pass. The user approved the overall look (2026-10-15).
- The light canvas is upsampled from per-tile values and dark tiles are set back to black, so the light-to-dark step sits on the tile boundary: the LINEAR filter softens it by half a canvas pixel (a quarter tile) on each side, and the lit tile next to a dark one darkens towards it.
- **Vision edges:** the client computes the view from its predicted (or interpolated) position, the server from its own, so a tile at the very edge can differ for a moment. A monster on a seen tile can stand partly in the drawn black (a tile counts when any of its 16 sample points is in sight). Walls count per tile by the tile FOV, so a wall the FOV marks can show whole although the polygon's shadow covers its face, and a wall face the polygon reaches outside the FOV stays black.
- The moving-light list uses a distance test without line of sight, so the glow of a shot or enemy behind a wall within range is sent and drawn (its carrier is not).
- An explosion's (and a healing wave's) flash is flat for its 0.4 s (0.6 s) and then gone (no fade-out). A shot without an explosion lights nothing at its impact once its own light is gone.
- Vision and darkvision: every number (vision per enemy in tiles, the boss 25 tiles, darkvision shares 0 / 1/3 / 1, the greyscale `DV_DARK` 0.45) is a first guess for the balancing pass. The humans' blindness in the dark makes the lich fight easier (disciples idle in the dark).
- The greyscale (`DarkvisionFX`) is a camera-wide post effect, so inside the darkvision range it also greys world-space damage numbers, HP bars and the E hint, not only the floor and figures. Per-object exclusion would need a second camera or layer.
- Light is refreshed once per tick before the AI (perception needs this tick's lights) and once more in `send_snapshots` on snapshot ticks. Positions move between the two; the snapshot refresh is the one the client must match, so the filter uses it. It costs one extra moving-light cast per snapshot.
- Each attach of `DarkvisionFX` compiles a new pipeline instance (F4 and the `?lights` V key cycle it, so this only happens in debug use); the mask texture is not primed at `LightView` construction.
- Hero melee, dashes and arrows next to a torch put it out (any non-heat hit does); this is the agreed rule, but it may prove annoying in play.
- Effects: the durations, the lich's cooldowns and the bosses' 0.5 effect resistances are first guesses for the balancing pass, and the lich's spells and the HUD icons have not been played live yet. The HUD icons are drawn symbols (`ui/effectIcons.ts`). Petrified uses a greyscale filter, so it shows only with WebGL. No effect has a sound, and Slowed, Accelerated, Frozen and Poisoned have no source yet (only F8 applies them). The status marks follow the figure's alpha and vanish with the effects when a creature starts to fall or drown.
- Torches are sent only when in the viewer's FOV, so a torch sprite can pop in at the edge of the FOV (under the darkness, so it is rarely noticeable). The lights themselves come from the start info and events and never pop.
- Weapon effects (swooshes, rings, particles) are drawn under the darkness, so they are black where it is dark, like the heroes (an explosion lights its own spot). The server still sends hurt and heal on a hero in the dark (`on_hero`); the client draws numbers on heroes and allies over the darkness, so they show, and numbers on monsters under it, so they vanish where it is dark.
- Snapshots are compact but not delta-compressed (every snapshot is complete). They are small anyway.
- Boss fights are covered by unit tests and were played live once against all three bosses; their numbers are not balanced yet.
- No password recovery, by design: there is no e-mail address to send anything to.
- Passwords travel in the login request. In production the game must run behind a TLS reverse proxy (with `COOKIE_SECURE=1`).
- Behind a reverse proxy every request comes from the proxy's IP, so the per-IP limits apply to everyone together. `X-Forwarded-For` is not read yet.
- The login limiter and the one-connection-per-account rule live in the memory of one server process.
- Admin sessions also live in memory: a restart logs the admin out. They end after `ADMIN_SESSION_MINUTES` without an admin action. There is one admin login, shared by whoever knows it; the audit log names it, not a person.
- Statistics count UTC days. Their history starts with the first deployment of the admin area.
- OpenTelemetry export is plain HTTP only (no TLS client built in).
